# 외부 호출 함수의 범위와 설계 기준

인터페이스는 “무엇을 요청하거나 확인할 수 있는가”를 나타내는 최소 계약입니다. 구현체의 내부 상태를 전부 노출하는 목록으로 만들지 않습니다.

`CanReceiveAction`, `ApplyActionAttempt`, `ResolveActionAttempt`처럼 가능한 요청과 적용을 표현합니다. 특정 대상에만 있는 방어막·약점·복구 함수를 모든 대상의 공통 계약에 넣지 말아야 합니다. UI가 필요한 수치는 상태 소유자의 조회나 별도 표시용 경로로 제공합니다.

변경 알림인 `OnHealthChanged`, `OnActionCompleted` 등은 상태·진행 담당자의 델리게이트로 분리합니다. 인터페이스에 조회·요청·이벤트 구독을 모두 섞지 않습니다.

진행률을 수행자가 관리한다면 시작·취소·진행 조회도 수행자 쪽에서 담당하는 것이 자연스럽습니다. 대상은 시도 수락과 최종 효과를 다시 검증합니다. 성공을 전제한 함수로 재검증을 건너뛰지 말아야 합니다.

구체적인 수행자 클래스에 의존하기보다 필요한 요청 정보나 역할 계약을 전달합니다. 선택 함수의 기본값이 미구현을 조용히 숨기지 않도록 필수 여부와 미지원 의미를 적습니다.

공유 구현과 상태가 필요하면 부모 클래스나 컴포넌트, 월드·게임 수명의 기능이면 서브시스템, 사건 관찰이면 델리게이트를 검토합니다. 인터페이스를 무조건 만들지 말아야 합니다.

언리얼 인터페이스는 실제 `UINTERFACE`·`UFUNCTION` 선언과 `Execute_함수명` 호출을 맞춰야 합니다. 블루프린트만 구현한 객체에 C++ 인터페이스 포인터가 있다고 가정하지 않습니다. 부작용 없는 조회만 `BlueprintPure`로 둡니다.

네임스페이스는 웬만하면 추가하지 말아야 합니다. 특히 언리얼 선언 매크로가 있는 자료형을 불필요하게 감싸지 않습니다.
