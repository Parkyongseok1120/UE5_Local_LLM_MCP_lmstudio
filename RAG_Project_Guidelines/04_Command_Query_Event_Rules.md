# 요청·조회·알림의 역할 구분

요청은 상태를 바꾸는 행동, 조회는 현재 값을 읽는 행동, 알림은 이미 일어난 일을 전달하는 행동입니다. 함수 이름과 호출 방향에서 구분되게 만들어야 합니다.

`SetHealth`처럼 값을 그냥 덮어쓰는 함수보다 `ApplyDamage`, `ConsumeAmmo`, `TrySpendResource`처럼 왜 바뀌는지 드러나는 요청을 우선합니다. 권한·비용·대기시간·대상·값 범위·변경 알림을 담당자 안에서 처리합니다.

이름만 바꾼다고 안전해지지는 않습니다. `AddHeat`, `BreakShield`, `CoolDown`도 외부에서 검증을 우회한다면 내부 함수로 제한해야 합니다. 디버그·초기화·단순 설정용 함수는 목적과 호출 범위를 따로 밝힙니다. GAS가 생성한 값 설정 함수도 일반 게임 외부 요청으로 소개하지 않습니다.

`Get`, `Find`, `Can`, `Is` 조회 안에서 객체 생성·에셋 로딩·알림 연결·상태 복구를 숨기지 말아야 합니다. 비용이 큰 검색과 캐시 갱신은 명시적으로 구분합니다.

상태 담당자가 값을 바꾸고 내부 상태를 정리한 뒤 알림을 발행합니다. UI·효과·오디오는 이를 보고 반응합니다. `OnRep`에서 서버 판정을 다시 실행하거나 보상을 중복 지급하지 않습니다.

수행자가 진행을 관리한다면 입력은 수행자에게 요청하고, 완료 시 대상에게 시도를 전달해 다시 검증받습니다. 공격자는 대상 체력·방어막을 직접 수정하지 않습니다. 연결한 콜백과 타이머는 종료 때 정리해야 합니다.
