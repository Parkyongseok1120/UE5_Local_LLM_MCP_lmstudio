# 0단계 기록 — 기준 실측과 조사 (2026-11-10)

[수정 계획](Harness_Editor_Authoring_And_Context_Revised_Plan_20261110.md)의 0단계 결과다. 모두 읽기 전용으로 확인했고 코드는 바꾸지 않았다.

## 1. 요약
- 같은 감사 프롬프트를 이전 빌드와 현재 빌드로 실행한 기록이 이미 있어서, 새로 실행하지 않고 그 두 기록으로 기준을 쟀다.
- 지난 수정은 실제 실행에서 효과가 있었다. 이전 빌드는 60라운드 한도 뒤 실패로 끝났고, 현재 빌드는 57라운드에 보고서를 완성했다.
- 현재 빌드에서 **새 결함 2건**을 확인했다. 보고서 검토 라운드가 내부 블록을 그대로 화면에 내보냈고, 검토 중 도구가 다시 열려 보고서가 한 번 더 작성됐다(3절).
- 수정 계획의 D5(압축 직후 목표 초과)는 수치로 확인됐다. 압축 6회 중 4회에서 최종 입력이 목표를 넘었다.
- Unity Bridge와 Unreal exporter의 관찰 공백을 표로 정리했다(5, 6절).
- 실제 실행은 빌드당 1회뿐이다. 모델 출력이 매번 달라지므로 수치 차이를 전부 수정의 효과로 볼 수는 없다.

## 3. 현재 빌드의 새 결함 (실제 실행에서 확인)

**결함 1 — 검토 라운드가 내부 블록을 화면에 내보냄**
- 52라운드(보고서 검토)에서 모델이 `[Delivered report — already shown to the user; write only what follows it]`로 시작하는 내부 데이터 블록을 끝 표시(`[End delivered report]`)까지 통째로 출력했다. 3,882자가 사용자에게 보였다.
- 기존 필터 두 개가 모두 놓쳤다. 중복 억제 필터는 출력이 보고서 본문으로 시작한다고 가정하는데, 이번에는 머리 줄이 먼저 왔다. 내부 데이터 필터는 모델이 빈 줄을 빼고 다시 쓴 블록을 원본과 같은 것으로 보지 못했다.

**결함 2 — 검토 라운드에서 도구가 다시 열려 보고서가 두 번 작성됨**
- 같은 52라운드에서 모델이 보완문 대신 "마지막으로 무기 생성/파괴 경로를 확인하겠습니다"와 도구 호출 텍스트를 냈다.
- 하네스가 이를 도구 재계획으로 처리해 조사를 다시 열었다(`fresh_tool_planning_retry_scheduled` → `read_recovery_resumed_original`). 3라운드 뒤 모델은 보고서 전체를 새로 썼다.
- 사용자는 보고서(51라운드), 내부 블록(52라운드), 새 보고서(56라운드)를 차례로 봤다.
- 지난 수정은 조사 한도로 끝난 경우에만 도구 재개방을 막는다. 보고서 검토는 그 조건에 들어 있지 않다.
- 두 번째 보고서는 첫 보고서의 미확인 항목(리스폰 시 무기 상태)을 실제로 확인해 내용은 더 낫다. 문제는 조사 자체가 아니라 중복 표시와 검토 단계의 "도구 없음" 계약이 깨진 것이다.

**관찰 — 결론 범위 판정이 걸리지 않음**
- 두 보고서 모두 "구조적 결함(P0/P1)은 발견되지 않았습니다"로 끝난다. 괄호가 낀 이 표현은 현재 정규식에 잡히지 않는다.
- 두 보고서 모두 미확인 범위 절을 스스로 적었기 때문에 이번에는 결과에 영향이 없었다.

## 7. 설정 스키마 (SDK 1.5.0)
- numeric 필드는 `min`, `max`, `step`, `int`, `precision`, `slider`를 받는다. 소수 한 자리 비율과 슬라이더로 스키마를 만들 수 있음을 확인했다.
- 필드에 `dependencies`와 `warning` 옵션이 있다. 방식이 `percentage`일 때만 비율 필드를 보이게 할 수 있을 것으로 보인다.
- 설명 문구는 고정 문자열이다. 실행 중 계산한 토큰을 설정 화면에 표시할 방법은 찾지 못했다.
- LM Studio 화면에서 실제로 어떻게 그려지는지는 확인하지 않았다.

## 8. 수정 계획에 주는 영향
1. **검토 단계 결함 2건을 먼저 고친다.** 사용자에게 바로 보이는 문제이고 지난 수정과 같은 영역이다. 퍼센트 예산(1단계)보다 앞에 둔다.
   - 보고서 검토 단계에서는 도구 재계획을 열지 않는다.
   - 전달된 보고서 블록을 머리 줄째 되풀이한 출력을 숨긴다.
2. **D5는 그대로 진행한다.** 6회 중 4회 초과가 실측으로 확인됐다.
3. **D3의 초기값은 유지한다.** 현재 구성에서 필수 입력 최대 26,863은 목표 46,323 아래다.
4. **1단계 측정에 system 구간 분해를 넣는다.** 필수 입력 증가의 대부분이 여기서 나온다.
5. **3절(Unity)과 5단계(Unreal)의 범위는 5, 6절의 공백 표를 기준으로 한다.**
6. **결론 범위 정규식에 괄호가 낀 표현을 추가한다**("결함(P0/P1)은 발견되지 않았습니다").

**후속 반영:** 1번(검토 단계 결함 2건)과 6번(괄호가 낀 결론 표현)은 이 기록과 같은 날 수정했다. 검토 라운드는 도구 호출 텍스트가 나와도 조사를 다시 열지 않고, 전달된 보고서 블록을 머리 줄과 끝 줄째 되풀이한 출력은 숨긴다. 실제 실행으로는 아직 확인하지 않았다.

## 9. 확인 방법
- 대화 JSON 두 개를 스크립트로 집계했다(디버그 이벤트, 도구 요청·결과, 사고 과정).
- Unity Bridge(`unity-editor-bridge/Editor/*.cs`), Unity provider 도구 계약, Unreal exporter 소스를 읽었다.
- 게임 프로젝트에서 `HealthRegenRate`, `HealthRegenDelay`, `RunSpeed`를 검색했다.
- SDK 타입 정의를 읽고 비율 필드 스키마를 실제로 만들어 봤다.
