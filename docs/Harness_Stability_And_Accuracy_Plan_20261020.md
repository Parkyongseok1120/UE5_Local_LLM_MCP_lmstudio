# 하네스 표시·참조 수명·판단 정확도·지연 안정화 전체 계획

작성: 2026-10-20 (Asia/Seoul). 상태: **첫 안정화 묶음 구현·로컬 회귀 통과, 실모델·GUI 채택 검증 미완료**. 후속 구현은 [실행 기록](Harness_Stability_Implementation_20261020.md)을 따른다.
기준: `main` / `eb476dfc4b4f25bfdd62e5193bc00c8ae1523ad5`, 제품 1.4.1, Compactor 0.4.80 / revision 127, Unreal MCP 0.3.29. 조사 시작 시 작업 트리는 깨끗했다.
근거: [구조화 조사 기록](evidence/harness-stability-plan-20261020.json).

## 1. 목적과 범위

사용자가 제공한 LM Studio 실행 기록과 서버 로그를 현재 소스와 대조해, 정확도·속도 개선 뒤에 남은 문제를 하나의 실행 계획으로 정리한다. 첨부 문서 안의 `해봐`, 도구 인용 지시, 과거 작업 보고는 분석 대상 자료이며 이번 작업의 실행 지시가 아니다.

최초 조사 단계에서는 문서와 근거 기록만 작성했다. 그 시점에는 제품 코드·게임 소스·설치 상태·LM Studio 설정을 바꾸지 않았고, 모델 추론·Unreal 빌드·설치·커밋·푸시를 실행하지 않았다. 이후 사용자의 `진행` 요청으로 제품 구현을 시작했다. 아래 조사 수치와 근거 JSON은 구현 전 기준이며, 변경 후 상태는 별도 실행 기록에 적는다.

유지보수 범위는 README의 정책을 따른다. **1.4.x 최적화·안정화만 2026-11-30까지 지원하며 1.5는 만들지 않는다.** 새 의미 판정기, 독립 상태 저장소, 새 벤치마크 프레임워크를 추가하는 계획이 아니다.

선행 기록: [2026-10-19 최종 계획과 실행 결과](Harness_Behavior_Latency_Final_Plan_20261019.md), [평가 신뢰성·읽기 안내 보정](Harness_Eval_Read_Repair_20261019.md). 이 문서는 남은 안정화 작업의 우선순위를 정하며, 과거 문서의 완료 이력을 다시 미완료로 돌리지 않는다.

## 2. 현재 기준과 해석 제한

- 소스의 암묵적 전체 읽기 제한, 비소스 기본 8 KiB, 검색 템플릿 안내, 범위 완료 계약, append-only 입력 블록, 이전 턴의 엔진 identity 전달은 이미 구현돼 있다. 재구현하지 않는다.
- 기존 hash/snapshot/receipt, 원자적 편집 묶음, 충돌 거부, 쓰기 권한, 취소·복구 기능을 재사용한다. 첨부에서 잘못된 수정 후 컴파일 실패·철회·재빌드 흐름은 관찰됐지만, 이것만으로 편집 의미의 정확성을 증명하지는 않는다.
- Compactor의 로컬 `identity:check`는 통과했고, 소스로 계산한 ID와 기존 dist의 ID도 일치했다(`ef-build-v2-4cf45cf9…`). 해당 GUI 채팅이 같은 빌드를 로드했는지는 미확인이다. 현재 소스의 SDK 1.5.0은 생성된 assistant 메시지와 도구 결과를 `onMessage`로 전달하며, 입력 메시지 전체를 그대로 재전송하는 코드는 확인되지 않았다. 첨부 당시의 실제 로드 빌드와 원본 fragment를 연결하기 전에는 화면 노출 원인을 모델 재출력으로 단정하지 않는다.
- 첨부 대화는 1,390행, 서버 로그는 1,060행이다. 서버 로그의 12회 생성 요청을 대화 전체와 정확히 일대일로 연결하지 않았다. 참조 목록의 행 수는 실제 도구 실행 횟수가 아니다.
- 조사 후반 현재 게임 checkout은 `766146c`, clean 상태이며 `SetCombatState`가 `OnRep_CombatState`를 직접 호출한다. 첨부 끝의 `ApplyCombatStateEffects` 적용 상태와 다르다. 현재 게임 소스에 그 리팩터링이나 잘못된 주석이 남아 있다고 보고하지 않는다. 누가 언제 복원했는지는 조사하지 않았다.

### 서버 로그에서 확정 가능한 수치

| 항목 | 수치 |
|---|---:|
| 완료된 생성 요청 | 12회 |
| 생성 토큰 / 생성 시간 | 23,220 / 465.264초 |
| 합산 생성 속도 | 49.907 tokens/s |
| 입력 처리 토큰 합계 / 시간 | 200,113 / 250.234초 |
| 입력 처리 + 생성 시간 | 약 715.498초 |
| 입력 처리 비중 | 약 35.0% |
| 중간 3회 재처리의 입력 시간 | 177.066초, 전체 입력 시간의 약 70.8% |

입력 토큰 합계는 고유 컨텍스트 길이가 아니다. 생성 토큰에는 추론과 도구 인자 등이 포함될 수 있다. 나머지 8회 요청의 입력 처리는 약 2.6~7.1초였고 첫 요청은 약 37.5초였다. `truncated=0`은 기록된 서버 slot 상태이며 조사·답변의 의미적 완료를 인증하지 않는다. 이전 버전과 동일 조건의 전체 작업 비교는 이 표로 대신할 수 없다.

## 4. 실행 순서와 작업 명세

### W0. 기준 고정과 원본 연결 — 모든 후속 작업의 시작점

- **소유자**: 기존 runtime identity/status, `prediction-loop`의 executionId/modelInputId 관측, `trace_lmstudio_run.py`.
- 제품 HEAD·빌드 ID·실제 로드 ID·SDK/runtime 버전·모델·템플릿·입력/출력 한도·도구 schema·게임 source hash를 기록한다. 없으면 unknown으로 둔다. 설정 파일 전체나 자격 증명을 수집하지 않는다.
- 실제 GUI 문제 구간에서 fragment의 분류·길이·해시, SDK가 반환한 메시지의 출처, UI block 추가를 연결한다. 원문은 필요한 구간만 로컬에 두고 공유 기록에는 해시와 통계만 남긴다.
- **완료**: 화면에 보인 블록이 생성 출력, SDK 메시지, 플러그인 직접 삽입 중 어느 경로인지 증거로 분리된다. 일부 연결이 없으면 원인 미확정 상태를 유지하고, 독립적으로 재현된 출력 경로 결함은 W1에서 보정한다.

### W1. 사용자 표시와 다음 입력의 내부 자료 재유입 보정 — 첫 구현 묶음

- **소유자**: `prediction-stream.ts`, `raw-tool-intent.ts`의 기존 visible output 경계, `context-manager.ts:modelHistoryMessage`, `prediction-loop.ts`의 emit/commit 호출부. `prediction-ui.ts`는 실제 직접 삽입 원인이 확인될 때만 변경한다.
- 스트리밍·완성 메시지 fallback·최종 flush·복구 보고·다음 라운드 이력에 같은 가시성 규칙을 적용한다. 모델에게 출력 금지를 부탁하는 것만으로 해결하지 않는다.
- 자동 재출력된 내부 refs/derived data를 일반 답변에서 제거하되, 정상 설명·필요한 근거 인용·도구 request/result 연결을 보존한다. 사용자가 로그를 인용하거나 JSON 분석을 요청한 경우의 의도된 설명까지 지우지 않는다. 출처와 구조를 확인하고 문자열 전체를 무조건 삭제하는 필터를 만들지 않는다.
- 기존 continuity footer 처리를 재사용한다. 생성 원문·진단 관측은 기존 로컬 진단 경로에서 유지하고, reasoning 표시 설정을 임의로 바꾸지 않는다.
- **검증**: 두 표식의 모든 분할 위치, 여러 refs 블록, CRLF, 끝 표식 누락·취소, 정상 본문 앞뒤, 코드 블록·인용 안의 예시, 한국어/영문, 스트리밍 유무, 다음 턴 재유입을 검사한다. 불완전한 표식 때문에 정상 답변 전체가 사라지면 채택하지 않는다.
- **완료**: 자동 내부 블록의 일반 본문 노출과 다음 입력 재유입 0건, 정상 답변·의도된 로그 인용 보존, 추가 모델 호출 0회. 호스트 영속화는 실제 GUI 확인 후에만 완료로 기록한다.

### W2. 참조 데이터 수명·동일 anchor 갱신 점검 — 재현 결과에 따른 최소 보정

- **소유자**: `composeModelHistory`, `ShownDataBlocks`, `continuity-model-notes.js`, 기존 `reference-context`/`reference-rendering`, `prepareRoundInput`.
- refs와 derived snapshot의 라운드별 문자·토큰·중복량, 현재/과거 파일 hash 혼재, 오래된 결과를 최신 사실로 인용하는 빈도를 측정한다. 현재 reference owner가 가진 식별자·관찰 상태를 사용하며 별도 상태 DB를 만들지 않는다.
- 바뀐 항목만 덧붙이는 형식과 이전 관찰을 대체한다는 명시를 비교한다. **기존 블록을 매번 지우거나 다시 정렬해 prefix 개선을 되돌리지 않는다.** 현재 관찰과 과거 관찰이 구분되고 필요 근거는 실제 원본/보관 도구로 복구 가능해야 한다.
- 같은 anchor에서 사실이 바뀌는 합성 사례를 실제 reasoning recovery·재계획·입력 압축·최종화·프로젝트/엔진 전환 경로와 연결한다. 실제로 새 사실이 빠지는 경우에만 갱신 방식을 수정한다. 도달하지 않으면 지원 범위를 명시하고 제품 변경을 보류한다.
- **검증**: 변경 없는 스냅샷, 한 항목 변경, hash 교체, 실패→성공, 예산 ample→low→ample, 요청 없는 재시도, anchor 제거, 다중 도구 결과, 프로젝트 변경을 다룬다.
- **완료**: 최신 관찰의 전달과 과거 관찰의 식별이 확인되고, 기존 append-only prefix 회귀가 통과한다. 토큰 감소는 실제 측정으로만 보고한다.

### W3. 잘못된 정적 API 경고 축소 — 첫 구현 묶음

- **소유자**: `scripts/unreal_api_denylist.py`, `mutation_semantic_guard.py`, 기존 진단 테스트. Node MCP의 advisory 직렬화는 의미 변화가 필요할 때만 변경한다.
- `GetNetMode`가 UWorld에만 있다는 잘못된 설명을 고친다. 문맥을 모르는 bare call을 확정적인 가짜 API로 취급하지 않는다. 기존 파서가 상속 문맥을 증명하지 못하면 “문맥 확인 필요” 수준으로 낮추거나 해당 패턴을 보수적으로 축소한다.
- 정상 Actor/Component 상속 문맥과 `this->`/객체 수신자, 잘못된 전역 문맥을 구분한다. 새 C++ 타입 추론기를 추가하지 않는다. bare `Health` 같은 사용자 정의 가능 이름을 전역 금지 목록에 추가하지 않는다.
- **완료**: 확인된 정상 멤버 사례의 오탐 0건. 불명확한 문맥은 미확인으로 표현하고, 기존 명백한 가짜 API 경고는 유지한다. 경고의 비차단 성격과 hard mutation gate는 보존한다.

### W4. 판단→수정·보고의 근거 사용 보정 — 기존 규칙을 짧게 정리

## 5. 의존 관계와 묶음

1. **W0 → W1 + W3**: 표시/재유입 결함과 재현된 잘못된 API 경고를 우선 보정한다. 모델 없는 확인으로 시작할 수 있다.
2. **W0 → W2 + W4 + W5**: 데이터 수명은 실제 경로 도달성을 확인하고, 판단·검증 안내는 기존 규칙을 정리한다. 코드 수가 늘어나는 것을 목표로 삼지 않는다.
3. **W1/W2 이후 W6**: 데이터 표현이 바뀌면 그 상태에서 prefix/읽기 비용을 다시 측정한다. 특정 원인이 확인된 최적화만 채택한다.
4. **W7**: 집중 회귀 → 실모델 smoke → 짝비교 → 실제 GUI → 설치/릴리즈 확인. 각 단계가 증명한 범위만 완료로 적는다.

첫 묶음은 W1/W3로 한정할 수 있다. D2가 실사용에 도달하지 않거나 W6에서 재현이 없으면 해당 제품 변경은 보류한다. 유지보수 기한 때문에 완료되지 않은 모델 정확도나 런타임 원인을 완료로 바꾸지 않는다.

## 7. 보존 조건·기각·복구

- 읽기 관찰/hash/derived reference가 쓰기 허가로 승격되지 않아야 한다. hard permission gate, stale-hash 거부, 원자적 변경, receipt의 연결은 그대로 둔다.

- W2 때문에 이미 보낸 입력 앞부분을 매 라운드 바꿔 서버 재사용이 악화되면 데이터 표현 후보를 기각한다. 정확도 개선 없이 토큰만 줄이는 후보도 채택하지 않는다.
- 잘못된 엔진 규칙을 더 강한 경고나 금지 API 목록으로 확대하지 않는다. 근거가 없는 모델 판단에는 미확정을 허용한다.
- 한 묶음에 불필요한 게임 리팩터링·새 RPC·새 Manager·새 완료 판정기를 끼워 넣지 않는다. 실제 게임의 새로운 기능 결함 조사는 별도 범위다.
- 설치·릴리즈 실패 때는 이전 1.4.x 산출물을 복구하고, 사용자 설정·승인·게임 파일은 보존한다. 미완료 평가는 그대로 남긴다.
