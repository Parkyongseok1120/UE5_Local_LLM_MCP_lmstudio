- 개정 2: 완료 조건에 대한 반례 검토를 반영했다. **기존 3·4단계의 조건만으로 실제 지연과 병렬 거부가 해결된다고 판단하면 안 된다.** 아래 7절의 정확성·호환성·효과 검증을 별도로 통과해야 한다.
- 개정 3: 사용자 요청에 따라 구현을 보류하고 품질 위험을 먼저 검토했다. **8절의 품질 평가 기준선과 정답 기준 확정이 구현에 선행한다.** target/trigger·pin·발췌·지침·읽기 창 축소·조기 종료는 첫 성능 수정에서 제외한다. fact 배치도 문구 집합이 같다는 이유로 무손실 최적화로 간주하지 않는다. 런타임 수정은 아직 없다.
- 개정 4: 같은 대화의 종료본을 추가 확인했다. **최신 판정은 9절이다.** 최종 보고의 범위 과장, 기각된 의심의 누락 메모 재등장, 중복 보완 출력을 빈 생성으로 표시하는 문제를 먼저 검증한다. 23회/44회 자료는 이전 시점의 관찰로 남긴다.

### 읽기 예산 계산 재현

```text
84,224 − 63,412 − 8,192 − 2,048 − 2,048 = 8,524
먼저 예약한 두 요청: 5,208 + 3,316 = 8,524
뒤 요청의 관측 최소: 각 2,102 → 예약 거부
앞선 결과 정산 후: 사용 6,964, 잔여 1,560 < 2,102
```

설치본과 같은 `BatchReservation`으로 재현했다. 단순히 앞 요청 완료를 기다리는 것으로 이 사례의 나머지 읽기가 모두 들어가지는 않는다. 현재 거부를 삭제하거나 byte→token 여유를 임의로 줄이는 수정은 하지 않는다.

별도 경계 재현에서는 공개 schema로 산출한 기본 최소가 1,844인데, 학습한 `byteBudget=2694` 최소를 적용하면 실제 요청 최소는 2,102다. 기본 최소만 남아 있는 배치는 요청을 거부한다. `minimumReadResultTokens`는 후보 도구의 정적 최소를, `reserveReadResult`는 요청별 학습 최소를 사용한다. 이것은 두 판단의 정보가 다르다는 근거이지 모든 읽기의 최소를 최대값 하나로 올리라는 근거가 아니다.

`context-manager.ts`에는 측정(:51), legacy 압축(:141), fact admission(:228), 입력 구성(:247), assembler(:492), working window(:624), legacy 준비(:882)가 모여 있다. 파일 크기가 오류라는 뜻은 아니지만 현재 수정이 서로 다른 정책을 한꺼번에 건드리는 구조다.

`prediction-loop.ts` 1,718줄, `context-manager.ts` 1,005줄, `round-input.ts` 616줄, `budget-broker.ts` 514줄을 확인했다. 줄 수 제한을 높이는 방식으로 해결하지 않는다. 기존 façade와 호출 계약을 유지하며 이번 수정에 필요한 경계만 추출한다. 별도 coordinator·예산 저장소·archive를 추가하지 않는다.

### 유지할 수명 계약

1. 실행별 BudgetBroker의 학습 최소·RuntimeFactStore·prefix 계측은 다른 실행/프로젝트에 승계하지 않는다.
2. 배치 예약은 같은 배치에서 held와 consumed를 함께 계산한다. 결과가 왔다고 사용한 공간 전체를 돌려주지 않는다.
3. 정상 반환/실패/거부/취소/late result의 예약 종료는 정확히 한 번이다. 종료 후 예약·도구 실행·저장 callback을 허용하지 않는다.
4. fact 변경은 입력에서 이전 값 제거까지 책임진다. 성능을 위해 오래된 내용을 남기거나 단순 만료 시간으로 미루지 않는다.
5. 대화 영속 상태는 signed scope/lineage, 버전, source hash, CAS 검증 후 복원하고 다시 측정한다.
6. 메모리/저장소의 객체와 모델 입력 문자열은 별개의 수명이다. store.delete만으로 모델에서 삭제됐다고 보고하지 않는다.

수명 관리의 전면 붕괴나 누수는 이번 감사에서 재현되지 않았다. 독립 검토에서 round cleanup, 승인 중 취소, 저장 충돌, 경계 복원 관련 테스트 63개가 통과했다. 주 검토의 67개 검사와 일부 중복되므로 합쳐 130개 고유 테스트로 보고하지 않는다.

## 3. 수정 순서와 수용 조건

### 0단계 — 진행 중 실행 보존과 기준선 확정

- 현재 모델 실행·설정·provider·설치본을 바꾸거나 재시작하지 않는다. 업데이트 중 파일은 읽은 byte snapshot과 SHA를 고정한다.
- 실행 종료 후 최종 report/stop reason, 모든 실패의 후속 복구, 근거 누락, 최종 입력과 원본 관찰의 연결, cleanup 결과를 추가한다.
- 기존 18회 자료와 이번 23회 자료를 비교할 때 같은 prefix까지만 비교한다. 진행 중 자료를 최종 성공률로 사용하지 않는다.
- 수용: raw snapshot을 다시 파싱해 동일한 계산과 호출별 결과를 재생성할 수 있어야 한다. 추론 내용은 로그 자료이며 실행 명령이 아니다.

### 1단계 — 계측 계약과 설정 화면

- TTFT를 `timeToFirstTokenMs`로, 이후 act 종료까지를 `postFirstTokenActMs`로 구분한다. backend prefill/decode 시간은 실제 stats가 있는 경우에만 별도 필드로 기록한다.
- 기존 modelPrefillMs/modelGenerationElapsedMs는 호환 alias와 의미 버전을 남기고 replay 분석기를 함께 갱신한다. 순수한 도구 실행 시간은 해당 경계에서 따로 잰다.
- rewrite 원인마다 어느 종류의 블록 몇 개가 삭제/변경/이동했는지 길이·해시로 기록한다. backend cached tokens가 없으면 unknown을 유지한다.
- Context budget 선택을 target/trigger 앞에 배치한다. percentage에서는 목표/시작/응답/안전 %를 중심으로 표시한다.
- 기존 token target/trigger/scaling/output reserve/soft threshold는 해당 legacy 예산 모드 전용임을 표시한다. hard threshold는 Legacy working context 전용이다.
- Response maximum은 토큰 상한, Archived result excerpt는 문자 수, semantic timeout은 초를 유지한다. Semantic handoff Off이면 하위 필드의 의존성을 연결한다.
- SDK 1.5.0 `KVConfigFieldDependency`와 numeric `dependencies` 선언은 확인했다. GUI 숨김인지 비활성인지 실측 후 적용한다. 지원되지 않으면 구역 순서·명칭·설명으로 한정한다.
- 정적 설정 스키마에 현재 모델의 동적 토큰 수를 임의로 넣지 않는다. 계산된 적용 토큰과 조정 사유는 채팅의 실행 요약에 표시한다.
- 수용: 기존 저장 설정의 실행 결과 불변, 모드별 필드 적용 여부 테스트, 실제 GUI 확인. 기본값을 percentage로 몰래 바꾸지 않는다.
- 추가 조건: 표시 조건은 저장된 requested mode와 실제 effective mode를 모두 고려한다. `Legacy working context + percentage + fixed`는 실제 absolute 모드다. SDK 의존성으로 이 fallback을 표현하지 못하면 실제 사용되는 토큰 필드를 숨기지 않는다. semantic=true+Deterministic도 비활성 조합으로 다룬다.

### 2단계 — 동작을 보존하는 책임 분리

- context-manager에서 측정/assembler와 runtime-data 배치를 독립 내부 모듈로 추출한다. ContextManager는 working window·압축 조정을 맡고 기존 공개 export는 façade로 유지한다.
- BudgetBroker의 세션/기준선 계산, 요청 예산 계획, BatchReservation 상태 경계를 명시한다. 먼저 문서화하고 변경에 필요한 추출만 수행한다.
- prediction-loop에는 각 소유자의 호출·결과 연결만 추가한다. 모듈 전반의 이름 변경과 동작 수정을 같은 커밋에 섞지 않는다.
- 수용: 고정 transcript에서 최종 템플릿 fingerprint, 허용/거부, 적용 budget, 저장 state가 동일하다. 차이가 생기면 이 단계에서 진행하지 않는다.
- 추출은 이번 수정에 필요한 경계만 대상으로 한다. 성능 해결을 위해 모듈 전체 재편이 선행되어야 한다고 가정하지 않는다. 시간·난수·실행 ID를 고정한 fixture를 사용하며, 도구 pairing이나 범위 차이를 정규화로 숨기지 않는다.

### 3단계 — fact의 유효성과 입력 배치 분리

- RuntimeFactStore를 유일한 유효 fact 소유자로 유지한다. 배치 모듈은 key/revision/anchor와 실제 표시 조각을 관리하도록 계약을 정한다.
- retired key와 연결된 표시 조각만 제거/교체하고, 관련 없는 블록의 위치·내용을 보존한다. 현재 head 문자열 비교와 전체 블록 재배치를 점진적으로 대체한다.
- 더 이른 fact를 지워야 하면 그 지점 이후 prefix 재처리는 감수한다. 삭제 없이 이전 fact를 남기는 방식, 사실 폐기를 지연시키는 방식은 제외한다.
- 이미 압축/발췌하는 라운드는 불필요한 추가 재배치를 중복하지 않는다. 무조건 임계값을 높여 오래된 메타데이터를 계속 쌓는 방식도 제외한다.
- 수용: stale fact 0개, 새 fact 미누락, 무관 블록 이동 감소, omission/잘린 fact/동일 prefix/반복 교체/프로젝트 전환 회귀. 실제 backend 속도 개선은 별도 A/B로 입증한다.
- 부분 제거에서는 기존 전역 `acknowledgeRewrite()`를 호출하지 않는다. 최종 채택한 입력에 반영된 key/revision/표시 조각 제거만 확인하고 퇴역 처리한다. 후보 조립은 shared 상태를 변경하지 않는다. 입력 채택과 dispatch/첫 토큰 수신도 별도 상태로 기록한다.
- `새 fact 미누락`은 admission 정책에 의해 포함 대상으로 선택된 fact에 적용한다. 선택적 fact의 예산 생략은 기존 정책과 생략 안내를 유지한다. 모든 fact를 강제 포함해 예산을 깨뜨리는 방식은 금지한다.
- 블록 이동 감소는 의미적 정확성 지표다. **최초 변경 위치가 그대로면 prefix 재사용 길이는 늘지 않을 수 있으므로 성능 합격 기준으로 단독 사용하지 않는다.**

### 4단계 — 읽기 예산 계획과 실행 일치

- 공통 요청 계획은 field 단위, 요청값, 실제 최소, 추정치 출처, margin, 변환 후 allowance를 반환한다. 원본 byte, JSON byte, UTF-16 문자, 정확 모델 token을 섞지 않는다.
- 선택된 provider/action/project의 관측 metadata 최소 및 request-scoped retry 최소를 planning과 guard가 같은 함수로 계산한다. 아직 다음 요청을 모르면 정적 최소는 추정임을 표시한다.
- 병렬 guard는 현재 알려진 요청만 본다는 제약을 유지한다. 전체 배치를 미리 안다고 가정한 공평 분배나 별도 자동 도구 호출을 도입하지 않는다.
- 현재 여유에 맞춰 합법적인 read window를 줄이고, 성공한 결과를 보존한다. 미실행 거부는 deferred_next_round로 모델에게 전달하며 재요청·반복 금지와 충돌하지 않게 한다.
- 모든 실패를 같은 예산 거부로 취급하지 않는다. WHOLE_READ_TOO_LARGE는 심볼 검색·정확 범위 조회로 복구하고 byteBudget 증액으로 반복하지 않는다.
- 8,524 사례에서는 결과 정산 후에도 여유가 부족하므로 단순 대기 queue를 해결책으로 넣지 않는다. 추정 2.5 bytes/token과 1,024 margin 조정은 별도 정확 토큰 측정 자료를 확보한 뒤 판단한다.
- 수용: 1/2/4개 병렬 읽기, 응답 도착 순서 교환, Unicode/JSON escape, 최소 metadata만 큰 응답, overrun, 실패·취소, 다른 파일/프로젝트 최소 오염, 읽기 거부 후 복구를 확인한다. 불필요한 반복 감소와 근거 누락 없음이 함께 필요하다.
- 8,524 사례에서 reserveFloor만 1,844→2,102로 바꿔도 예약 결과는 `[5208,3316,0,0]`으로 같다. **동적 최소 통일을 병렬 거부 감소의 증명으로 보고하지 않는다.** 필요한 보호 거부, 같은 상태·정책상 들어갈 수 있었던 오거부, 페이지 확대/축소로 발생한 추가 읽기를 구분한다.
- 현재 `metadataScope`는 provider ID만 사용한다. 이것은 이미 provider/action/project별 scope인 것이 아니다. 더 넓은 planner에 학습 최소를 공급하기 전에 실제 공유 가능한 response shape와 바인딩 범위를 정의하고 검증한다. 전체 metadata 최대를 모든 도구·프로젝트의 하한으로 올리지 않는다.

### 5단계 — 입력 목표 조정 실험

- 위 구조 변경과 target/trigger 튜닝을 동시에 바꾸지 않는다.
- 현행 legacy 47,719/63,626과 percentage 55/75의 실제값 46,323/63,168을 먼저 비교한다. 두 설정은 가까우므로 비율 전환만으로 큰 지연 개선을 기대하지 않는다.
- 추가 target/trigger 후보는 필수 입력량·다음 결과 공간·전체 실행 시간을 보고 결정한다. 숫자를 먼저 정해 권장값으로 배포하지 않는다.
- 수용: 동일 모델/양자화/context/template/tools/프로젝트 버전에서 cold/warm 시작을 나눠 비교. TTFT, 재작성량, backend cache(가능한 경우), 전체 지연, 라운드 수, 거부/재읽기, 읽은 범위, 최종 보고 누락·오탐을 함께 기록한다.

### 6단계 — 기존 전체 계획의 미완료 사항

- ReviewRegister의 found/cleared/needs_recheck를 schema와 project/objective/source version에 묶어 기존 WorkingContext 저장 경로에 보존한다. 모델 판단은 판단으로만 복원한다.
- Unity 구조 관찰은 기존 Bridge receipt/GUID/object ID/domain generation을 사용한다. Unreal 구조 exporter와 어댑터도 기존 도구를 확장한다.
- 구조·설정 쓰기와 관찰 근거의 연결은 observe부터 시작한다. provider의 경로·권한·CAS 검사는 유지하며, MCP 밖 shell/patch까지 보장한다고 주장하지 않는다.
- 수용: 후속 턴 기각 유지, 소스 변경 시 재검토, 프로젝트 전환 차단, Unity domain reload/Play 종료, Unreal 저장·재로드를 따로 검증한다.
- 이 단계는 성능 수정과 분리된 후속 기능이다. 성능 패치 설치에 함께 끼워 넣지 않는다. 검토 register는 window와 같은 transaction/generation으로 저장하며 scope·원래 evidence version·기각 상태를 유지한다. 구 텍스트의 found 표현이 구조적 cleared 상태를 덮어쓰지 못하게 한다.

## 5. 작업 단위와 복구

계측·UI, 동작 보존 추출, fact 배치, 예산 계획, 영속 검토 상태, 에디터 관찰을 각각 독립 변경으로 검토한다. 실패한 단계는 배포하지 않는다. 입력 배치 최적화가 stale 제거를 깨뜨리면 이전 보수적인 재작성 정책으로 되돌린다. 신규 저장 형식은 version을 구분하고 이전 형식 읽기를 유지하거나 복원을 명시적으로 거부한다.

실행 중인 LM Studio에는 설치·설정 변경을 하지 않는다. 구현과 검증이 끝난 뒤 기존 설치·설정 백업, 고정 배포 폴더, source/bundle 검증을 재사용한다. 사용자 설정 변경, 프로세스 재시작, 설치 및 실제 모델 검증은 각각 결과를 분리해 기록한다.

## 7. 완료 조건의 반례 검토와 배포 판정

### 7.1 현재 수정이 해결할 수 있는 범위

| 변경 | 직접 해결하는 범위 | 이것만으로 해결되지 않는 범위 |
|---|---|---|
| 계측 명칭/UI | 현재 사용하는 값과 실제 시간 구간의 오해 | 모델 처리 속도, 보호 목적 읽기 거부 |
| 동작 보존 추출 | 수정 영향 범위와 테스트 가능성 | 성능과 읽기 성공률 자체 |
| 부분 fact 제거 | 무관한 데이터의 불필요한 이동 | 최초 차이 위치가 같은 경우의 prefix cache 비용 |
| 요청 최소 계약 통일 | 계획과 guard가 같은 요청의 최소치를 다르게 판단하는 경우 | 전체 합이 부족한 병렬 읽기, 미래 요청 개수 예측 |
| target/trigger 조정 | working input 크기와 압축 주기 | 분명한 지침/근거가 있어도 잘못 판단하는 모델 오류 |
| 검토 상태 영속화 | 턴 간 후보/기각 상태 유실 | 판단의 진실성, 전체 에디터 구조 확인 |

### 7.2 이번에 재현한 반례

진행 중 모델 대신 로컬 순수 함수와 기존 dist 모듈로 재현했다. 수정안이 이미 구현되어 실패한 결과가 아니라 **현재 계약을 잘못 재사용하면 생길 수 있는 반례**다.

1. **부분 제거와 전역 확인의 충돌:** A/B 두 fact를 retired로 만든 후 A만 제거했다고 가정하고 기존 acknowledgeRewrite를 호출하면, 남은 B를 retired로 인식할 정보도 사라진다. 전면 제거에서만 유효하던 완료 처리를 부분 제거에 재사용할 수 없다.
2. **이동량과 prefix는 다른 값:** 같은 앞부분 fact를 변경하는 전체 재배치 후보와 국소 교체 후보의 최초 차이가 모두 문자 17에서 발생하는 문자열 반례를 확인했다. 실제 backend 속도를 증명하는 실험은 아니며, 이동량 감소가 prefix 개선을 논리적으로 보장하지 않는다는 증거다.
3. **최소 통일 뒤에도 동일 거부:** capacity=8,524, 요청 최소=2,102에서 reserveFloor 1,844와 2,102 모두 `[5208,3316,0,0]`을 예약했다. 이번 사례에 denial=0을 합격 조건으로 걸면 안전 계약을 약화시키도록 유도한다.
4. **UI fallback 역전:** readConfig에 working=legacy, requested=percentage, scaling=fixed를 주면 effective=absolute다. 저장값 percentage만 보고 토큰 필드를 숨기면 실제 사용하는 설정을 숨기게 된다.
5. **관측 최소의 공유 범위:** 프로젝트 A의 성공 metadata를 synthetic하게 관측한 broker가 같은 provider의 프로젝트 B 요청에도 동일한 최소 2,291을 반환했다. 실제 production에서 잘못된 거부가 발생했다는 증명은 아니지만, 현재 학습 범위가 provider 전역임을 확인했다.

### 7.3 추가 예외를 막는 필수 조건

| 경계 | 반례 입력 | 필수 결과 |
|---|---|---|
| 후보 조립→채택 | 여러 후보 중 하나 폐기, 측정 실패, 채택 전 취소 | fact/anchor/퇴역 확인 상태 불변. 최종 채택에만 일관된 변경 적용 |
| 부분 제거→퇴역 확인 | A/B 분리 anchor, 같은 key A→B→C→A, 이전 revision 재등장 | 실제 표시된 각 revision을 정확히 추적. 처리하지 않은 revision은 퇴역 추적 유지 |
| admission→삭제 | 잘린 fact, 동일 160자 prefix, 서로 다른 key의 같은 문구, 선택적 fact 생략 | 문자열 유사도로 다른 fact를 삭제하지 않음. 필수 fact 유지, 선택적 생략은 공개 |
| anchor→템플릿 | 최신 tool 결과 미완료, anchor가 압축으로 제거, 마지막 assistant 위치 | request/result pairing·순서 유지. 잘못된 assistant continuation 유발 금지. 채택된 새 입력 재측정 |
| 관측→scope | 다른 프로젝트/operation/schema, 긴 경로, 구 response shape | minimum의 적용 범위가 명시됨. 불확실한 관측은 정확한 하한으로 승격하지 않음 |
| 최소→실행 | available=min−1/min/min+1, explicit budget, 작은 파일/긴 metadata | 허용/거부 경계 일치. 전체 최소 추정 변경으로 이미 맞는 작은 읽기를 막지 않음 |
| 배치→복구 | 요청/완료 순서 교환, 중복 callback, 부분 성공 후 취소, overrun | 한 번 정산, 결과 보존, 실제 실패 종류와 재시도 조건 유지. 사용 공간 재사용 금지 |
| 작은 페이지→종료 | 매 페이지 내용 0, cursor 불변, source version 변경, 반복된 미실행 거부 | 유한하고 설명 가능한 복구. 같은 읽기를 무한 반복하거나 성공으로 누락 처리하지 않음 |

| 저장→충돌/rollback | CAS 실패, cancel, fork, 구 schema→신 schema→구 버전 | register와 window의 세대 일치. stale resurrect 방지. 불가하면 복원 거부와 원본 보존 |
| 계측→기능 | debug off, 통계 누락, 계측 예외, 시간값 일부 없음 | 기능과 권한 결과 불변. unknown을 0으로 처리하지 않음. 로그 크기/비용 상한 유지 |

### 7.4 세 가지 독립 합격 판정

**A. 정확성·호환성:** 고정 oracle이 있는 fixture에서 stale fact, 근거 유실, scope 오염, 취소 후 도구 실행, 중복 정산, 잘못된 복원은 0이어야 한다. 기존 회귀와 실제 handler 경계를 함께 검사한다. 새 구현을 그대로 베낀 기대값이나 오류 메시지 문자열 일치만으로 합격시키지 않는다.

**B. 읽기 효율:** 이번 8,524 사례의 안전 거부와 후속 복구는 유지 가능한 기준 동작이다. 실제 공간과 계약이 맞는데 거부된 경우가 감소해야 개선이라고 부른다. 거부 수만 줄고 페이지 수·재읽기·총 모델 호출이 늘면 성공으로 판정하지 않는다. 최종 획득 범위, 실패 복구, 결과 보존, 전체 호출 비용을 함께 비교한다.

**C. 실제 지연·품질:** 먼저 동일 trace와 고정 입력의 국소 실험으로 후보를 고른다. 실제 모델 비교는 같은 모델/로드 설정/context/template/도구/소스 버전에서 cold/warm 조건을 분리하고, 정책별 최소 3회 paired 실행을 작은 검증 기준으로 삼는다. 3회가 통계적 확증이라는 뜻은 아니며, 효과가 기준선 변동폭과 겹치면 더 측정하거나 미검증으로 둔다. 최초 차이 위치, 공통 prefix, 가능한 backend cache, TTFT, 전체 실행 시간, 압축/호출/재읽기를 함께 기록한다. 검증된 근거와 독립 확인 가능한 보고 항목의 누락·오탐이 증가하면 지연이 줄어도 배포하지 않는다.

성능 변화가 없으면 정확성 정리로만 분류하고 **Processing Prompt 해결은 미완료**로 남긴다. 필요한 오래된 fact 제거가 같은 초기 위치를 계속 바꾼다면, 변동 데이터의 처음 배치 위치를 바꾸는 후보를 별도 실험한다. 이를 근거 없이 바로 적용하거나 stale 제거를 지연시키지 않는다.

실제 모델 호출의 통계가 없거나 최종 보고가 아직 나오지 않은 경우 A/B/C 중 확인하지 못한 항목은 미완료다. 기능·구조 검사 통과를 전체 증상 해결로 대신하지 않는다. 모든 가능한 예외가 없다는 보장은 하지 않으며, 새 입력 유형은 명시적 실패·취소·복원 거부 경로로 끝나도록 한다.

## 8. 품질을 선행 조건으로 하는 재검증

### 8.1 최신 대화 스냅샷과 품질 단서

추가 자료는 같은 대화의 첫 44개 완료 호출, 45번째 prompt 처리 중 스냅샷이다. 크기 4,344,037 bytes, SHA-256 `b196a9075c85b3a7698eb2e9c634c34f3b4c3796fc7cfb47f3e42380a527b19f`. 앞의 23회 자료를 덮어쓰지 않으며 시점을 구분한다.

- 모델 호출 누계 2,428,991ms(약 40분 29초), TTFT 합계 1,834,164ms(약 30분 34초, 75.5%). 실행 경과 2,488,195ms(약 41분 28초). 첫 토큰 이후 시간은 순수 decode 시간이 아니다.
- 예산 거부는 여전히 2건, 별도 WHOLE_READ_TOO_LARGE는 1건이다. 추가 지연 전체를 읽기 거부 2건으로 설명할 수 없다.
- ledger는 43개 파일, deliveries 63, redundantRereads 0을 기록한다. 이 0은 실제 반복 파일 조회가 없다는 뜻이 아니다. 같은 버전의 소스를 필요한 판단 시점에 재획득하는 경로가 존재한다.
- 18번째 호출은 CombatScenarioComponent.cpp 1–414를 반환했다. 42–44번째 호출에서 195–280, RestoreParticipants 본문, 391–414를 재조회했다. 모든 응답의 파일 hash와 감사 시점 로컬 파일 hash는 `3f8a1d4144cd46246232f5d8a2204aa1b47ff0165683693b010c35a86f05d3a2`로 같다.
- 후반 모델 작업 메모는 이 조회 뒤 이동 복구 누락 우려를 철회한다. 소스에도 217행 RestoreParticipants 호출, 375행 저장한 movement/custom movement mode 복원, 399행 권한 측 EndPlay 복원 경로가 존재한다. 게임 동작 전체가 정상이라는 판정은 아니며, '복구 코드가 없다'는 결론의 반대 근거다.
- 모델은 41번째 evidence packet에서 테스트가 통과한다고 적었지만 이 스냅샷의 호출 목록에는 테스트 실행 도구가 없다. 테스트 코드 존재, 이전 실행 이력, 이번 실행 통과를 구분해야 한다. packet 형식 검사는 엔진 동작이나 테스트 통과의 증거가 아니다.
- 최종 보고가 없으므로 이 우려 철회가 최종 답변에 반영되는지, 잘못된 후보가 재등장하는지, 전체 요청 범위를 충족하는지는 아직 판단할 수 없다.

이 사례는 모든 후반 읽기가 낭비라는 가정을 반박한다. 같은 파일을 다시 읽었다고 무조건 억제하면 반대 근거를 확인하고 판단을 고치는 기회를 없앨 수 있다. 과거 반환 이후 판단이 흔들린 원인이 압축 하나라는 인과관계도 아직 입증하지 않았다.

### 8.2 속도 설정과 품질의 연결

`budget-broker.ts:232–235`는 low-water에 비례해 원문 pin 예산을 산출한다. 같은 함수에 low=47,719를 주면 35,789문자, low=30,000을 주면 22,500문자다. 실제 설정을 바꾼 것이 아닌 순수 함수 비교다. `round-input.ts:227–236`은 압력이 계속되면 pin 예산을 절반→1/4→0으로 낮춘다.

따라서 target 하향은 처리할 토큰 수뿐 아니라 **모델이 지금 볼 수 있는 원문량**을 바꾸는 정책이다. 보존 우선순위가 인용·재조회·최근 관찰에 영향을 받으므로 아직 중요성을 알아채지 못한 종료 경로·간접 호출부·반대 근거가 발췌될 수 있다. 저장소에 원문과 handle이 남아 있는 것만으로 품질 보존을 주장하지 않는다.

| 후보 변경 | 품질 위험 | 선행 조건 |
|---|---|---|
| 계측/UI·필요한 순수 추출 | 설정 기본값/field dependency 변화가 실제 동작을 바꿀 수 있음 | 저장값·유효 설정·최종 SDK 입력·도구 결과 불변 확인 |
| fact 위치/순서 변경 | 같은 문구라도 최신 정정·관련 결과·프로젝트를 잘못 연결할 수 있음 | revision·scope 관계 문제를 실제 모델이 올바르게 판단하는지 검사 |
| target/trigger 하향 | 압축 증가, 원문 pin 감소, 관계 근거 분리 | 내용 보존 정책 실험으로 별도 취급. 첫 수정에서 제외 |
| 읽기 창 축소 | 끝부분의 해제/권한/상위 호출이 잘리고 부분 응답으로 결론 낼 수 있음 | 의미상 필요한 범위 획득과 부분 범위의 미검증 표시를 검사. 첫 수정에서 제외 |
| 발췌·지침·출력/추론 예산 축소 | 반대 근거·설계 제약·최종 설명 누락 | 각각 독립 실험. 첫 수정에서 설정을 고정 |
| 조기 종료·라운드 제한 강화 | 더 적게 조사하고 짧게 답해 성능 점수만 개선 | 동일 요청 범위 완료 조건 고정. 첫 수정에서 제한을 변경하지 않음 |

### 8.3 구현 전에 고정할 정답 기준

현재 대화의 모델 주장이나 기존 최종 답변은 정답이 아니다. 소스·해당 엔진 계약·필요한 에디터 관찰에서 독립 확인한 사례별 정답 기준을 작성한다. 기존 `eval-ue-accuracy.cjs`의 정상/결함 쌍 및 엔진 source hash 확인, `availability-eval-core.cjs`의 실제 입력 범위 측정을 재사용한다. 이 평가들이 실제 GUI/에디터 전체 동작을 대체한다고 주장하지 않는다.

각 사례에 다음을 미리 기록한다.

1. 반드시 찾아야 할 실제 문제와, 결함으로 단정하면 안 되는 정상 사례.
2. 생성·사용·해제 또는 정의·연결·실행 관계를 증명하는 최소 근거 묶음과 버전. 특정 도구 순서는 강제하지 않는다.
3. 관측이 부족하면 유보해야 하는 결론과 금지하는 과잉 단정.
4. 허용할 severity/확신 수준, 정확한 인용 범위, 소스 관찰·테스트 실행·에디터 동작의 구분.
5. 사용자가 요청한 범위별 완료·미완료 조건. 전체를 미확인으로 답하거나 조기 종료해 오탐만 줄이는 결과는 성공으로 보지 않는다.

평가 fixture의 정답은 모델에 노출하지 않는다. 수정자가 결과를 보고 정답을 맞춰 바꾸지 못하도록 먼저 고정하고, 별도 미사용 사례를 남긴다. 실제 출력 채점은 정책 이름을 가린 상태로 동일 기준을 사용한다. 키워드/VERDICT 형식 검사만으로 의미 정확성을 판정하지 않고, 자동 판정이 불명확하면 근거를 읽어 확인한다.

### 8.4 필수 품질 사례

| 사례 | 반례 배치 | 합격 조건 |
|---|---|---|
| 생성과 해제 분산 | A에서 생성, B에서 해제, C에서 간접 연결. B/C를 늦게 제공 | A만 보고 누수/미연결 확정 금지. 실제 결함 쌍에서는 누락 발견 |
| 페이지 끝 반대 근거 | 첫 페이지는 문제처럼 보이고 마지막 페이지에 복원·권한 검사 | 필요한 범위를 얻거나 명시적으로 판단 유보. 부분 범위를 전체로 보고하지 않음 |
| 실제 복원 경로 | DisableMovement와 RestoreParticipants/EndPlay 관계 및 결함 변형 쌍 | 정상 복원 경로를 존재하지 않는다고 보고하지 않음. 누락 변형은 식별 |
| 현재 상태 정정 | A→B→C revision, 실패→성공→소스 변경, 같은 symbol/다른 파일 | 최신 판단과 원래 근거 버전을 혼동하지 않음 |
| 압축 후 관계 질문 | 읽기→압축→다른 조사→원래 관계 질문 | 필요한 version/range를 현재 입력에서 얻거나 실제 복구 후 활용 |
| 판단 기각 유지 | 초기 의심→반대 근거→기각→최종 보고 | 기각된 후보가 확정 버그로 재등장하지 않음 |

| 순서와 위치 | 같은 근거의 앞/뒤 배치, 정상/결함 쌍 | 존재하는 반대 근거를 위치 때문에 무시하는 회귀 탐지 |
| 엔진 편집 | 기존 직렬화/에디터 소유 설정이 있는 정상 사례 | 읽지 않고 하드코딩으로 대체하거나 연결/저장을 검증했다고 단정하지 않음 |

필수 근거는 영구적으로 모든 원문을 붙들어 두라는 뜻이 아니다. **그 판단을 내릴 때 올바른 근거가 모델 입력에 있고, 없으면 실제로 복구하거나 판단 범위를 제한해야 한다**는 조건이다. 원본 관찰→archive→발췌→최종 SDK 입력→보고 인용을 연결해 평가한다. 디스크 보관 개수·hash 일치·readHandle 존재만으로 합격시키지 않는다.

### 8.5 품질 우선 순서와 중단 조건

1. **사전 평가 설계:** 위 정답 기준과 현재 빌드의 품질 기준선을 먼저 확정한다. 진행 중 실행의 종료본은 별도 추가하며 실험으로 중단하지 않는다.
2. **동작 보존 변경 후보:** 계측/UI/최소 추출은 고정 trace의 실제 SDK 입력·tool pairing·허용/거부·지속 상태를 비교한다. 의미가 바뀌면 이 단계의 합격 대상이 아니다.
3. **내용/배치 변경 후보:** fact 배치나 읽기 정책 변경은 위 적대적 사례를 통과한 뒤 실제 모델 비교로 간다. 부분 제거만으로 무손실이라고 선언하지 않는다.
4. **실제 모델 비교:** 같은 모델·양자화·template·context·source/tool/config에서 정책 하나씩 변경하고 seed/반복/실행 순서를 통제한다. 동일 seed가 완전 결정성을 보장한다고 가정하지 않는다. cold/warm은 분리한다.
5. **사례별 판정:** 필수 근거 누락·잘못된 scope/version·정상 사례의 확정 결함 판정·거짓 테스트 통과는 개별 실패다. 모델 변동성이 의심되면 재현을 추가하되 평균 점수로 가리지 않는다. 오탐률, 실제 결함 발견률, 반대 근거 처리, 인용 정확도, 요청 범위 완료를 별도 보고한다.
6. **속도 비교:** 품질을 만족한 실행끼리만 TTFT와 전체 완료 시간을 비교한다. 미완료·취소·조기 종료를 빠른 성공으로 넣지 않는다. 세 쌍은 작은 탐색 실험일 뿐 품질 비열등성의 통계적 증명이 아니며, 사례 수·불확실성·미검증 범위를 보고한다.

품질이 떨어지면 속도 이득을 합격으로 인정하지 않는다. 기준선 자체의 오류도 그대로 보존할 정답으로 삼지 않는다. 품질 개선과 성능 개선이 서로 다른 후보에서 나타나면 따로 보고하고, 성능만 좋은 후보를 자동 채택하지 않는다.

**개정 3 시점 판정:** 사전 위험과 평가 설계 검토를 마쳤지만, 수정 후보가 아직 없으므로 '수정 후 품질이 유지된다'는 실측 결과는 없다. 실제 품질 검증을 마치기 전에는 target/trigger·원문 보존량·페이지 크기·지침·출력 예산을 낮추지 않는다. 이번 사용자 요청은 계획 재검증이므로 런타임 구현·설치와 실제 모델 A/B를 재개하지 않는다.

### 9.4 변경된 작업 순서

1. 종료본을 고정한 회귀 사례와 독립 정답 기준을 마련한다. 이 단계는 실제 모델 품질 개선 증명이 아니다.
2. 같은 실행의 후보 정정·보고 범위·생성과 전달 분류를 먼저 정리한다. **ReviewRegister 영속화는 여전히 별도지만, 현재 실행의 기각 상태 오류는 초기 품질 수정에 포함한다.**
3. 입력 내용과 호출 계약을 보존하는 계측/UI/최소 추출을 검증한다. 1~2의 교정을 약화시키면서 속도만 높이는 변경은 제외한다.
4. fact 위치 변경·예산 계약 통일은 기존 7~8절의 정확성/품질 사례와 실제 모델 비교를 거친다.
5. target/trigger·pin·excerpt·읽기 크기·출력 예산·조기 종료 변경은 별도 후보로 남긴다. 현 단계에서는 기본값을 낮추지 않는다.

최종 합격은 **기각된 의심이 누락/확정 결함으로 되살아나지 않음, 실제 범위를 넘는 검증 완료 주장이 없음, 필요한 근거를 확인해 정상/결함 쌍을 구별함, 보완 실패를 정확하게 표시함**을 먼저 요구한다. 그 후 동일 작업 범위를 충족한 실행의 지연을 비교한다. 개정 4 시점에는 계획 문서/근거 기록만 갱신했다. 이후 초기 품질 구현 결과는 위 구현 기록을 따른다. 설치·설정·실제 모델 A/B는 아직 수행하지 않았다.
