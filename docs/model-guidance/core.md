# 작업 공통 기준

범위: 코드 작성·수정·검토에 참고하는 원칙. 프로젝트의 명시적 요구, 실제 소스, 적용 버전의 계약과 함께 해석한다.

<!-- guidance-section: ownership -->
- 변경 전에 관련 상태의 결정권자, 호출 시작점, 실제 변경 지점, 종료 책임을 찾는다. 주석의 “SSOT”, “서버 권한”, “설정 가능”을 구현의 증거로 삼지 않는다.
- 설정 → 생성·등록 → 호출 → 상태 변경·외부 결과 중 작업에 필요한 연결을 확인한다. 함수·에셋·속성의 선언만으로 기능이 완성됐다고 보고하지 않는다.
- 같은 규칙의 확정 경로를 하나로 유지한다. 설정, 실행 상태, 복제·예측·표시값은 구분하고 갱신 관계를 명확히 한다.
- 기존 책임자가 맡을 수 있는 수정은 그곳에서 해결한다. 패턴은 실제 변경·수명 문제를 줄일 때 선택한다.
- 설정 추가는 선언 → 초기화 → 실제 소비 → 관찰 가능한 효과를 연결하고, 기본값과 다른 값으로 확인한다. 소비자가 여전히 상수를 쓰면 설정 추가만 완료된 것이다. 단위·범위·유한값 정책은 해당 입력 경계의 소유자에게 둔다.
- 캐시·추상화·방어 코드는 필요한 비용/실패 근거가 있을 때 추가한다. 값싼 getter를 캐시하면 교체·초기화·해제 책임이 늘어날 수 있다. 정상 코드와 변경이 불필요한 대안도 검토한다.
<!-- /guidance-section: ownership -->
<!-- guidance-section: lifetime -->
- 실패·취소·중복 호출·객체 종료가 관련된 변경에서는 상태와 후속 효과가 어떻게 남는지 살핀다.
- 캐시·이벤트·비동기는 생성/준비 → 사용 → 교체/재활성화 → 종료와 늦은 결과를 함께 대조한다. 취소 요청은 실제 중단이나 이미 발생한 효과의 롤백을 증명하지 않는다.
<!-- /guidance-section: lifetime -->
<!-- guidance-section: api -->
- 새로 도입·변경하는 외부 API와 진단에 충돌한 계약은 적용 버전의 사용 표현식·수신 타입·선언·인자·부모·매크로를 확인한다. 동일 버전·동일 계약의 확인 근거는 재사용한다. 같은 가설로 추측 수정을 반복하지 않는다.
- 컴파일 수정에서는 입력·결과·부모 호출·콜백·복제·충돌 필터의 의미를 보존한다. 의미를 바꾸는 경우 요구와 근거를 설명한다.
- 부분 발췌에 멤버가 없으면 선언·부모·조건부 컴파일과 검색 범위를 먼저 확인한다. 헤더 포함, 모듈/어셈블리 참조, Runtime/Editor·빌드 대상 문제를 구별한다. 같은 실패 가설로 헤더 경로를 바꿔가며 빌드를 반복하지 않는다.
<!-- /guidance-section: api -->
<!-- guidance-section: style -->
- 상태 대입과 조건을 읽기 쉬운 줄과 블록으로 작성한다. 기존 들여쓰기, 중괄호, 의미별 빈 줄을 따르고 역할을 드러내는 이름을 쓴다.
<!-- /guidance-section: style -->
<!-- guidance-section: proof -->
- 읽기 전에 미확인 질문과 필요한 선언·함수·호출 범위를 정한다. 입력에 있는 동일 버전의 근거와 기각한 가설을 재사용한다. 전체 파일은 필요할 때 읽고 매 페이지를 길게 재서술하지 않는다.
- API 사용·누락 가설은 적용 버전의 선언·부모·수신 타입·인자·의미를 확인한다. 부분 발췌와 검색 실패는 부재 증명이 아니다. 같은 실패 가설로 추측 수정을 반복하지 않는다.
- 상태·콜백은 소유자, 초기화 준비, 권한, 중복, 실패·취소, 종료·늦은 결과를 대조한다. 선언·등록은 실제 호출·효과 증명이 아니다. 초기화·부모·호출자의 반례를 확인하기 전 결함 등급을 확정하지 않는다.
- 완료 항목은 실제 성공 반환과 적용 내용 또는 현재 소스/diff에 연결한다. 파일명·hash·이전 요약으로 수정 내용을 만들지 않는다. 근거가 없으면 미확인으로 남기고 반증된 설명은 정정한다.
- 번호 작업은 사용자가 선택한 원문을 유지한다. 새 계획으로 번호 의미를 바꾸거나 기존 코드를 이번 성과로 보고하지 않는다. 적용·검증·미확인을 짧게 기록한다.
- 검증은 바뀐 계약을 관찰한다. 소스 확인, 변경 적용, 빌드 성공, 실제 동작은 구분한다. up-to-date는 새 컴파일 증명이 아니며 빌드는 원격 동작·입력·수명의 실행 증명이 아니다.
- 이 자료를 도구 실행의 추가 허가 조건으로 만들지 않는다. 문서 ID·경로만 받았다면 본문을 읽은 것으로 가정하지 않는다.
- 부분 결과(hasMore·truncated·nextCursor·부분 투영 notice)는 이어 받기 전까지 읽지 않은 범위로 다루며, 부분 검색으로 부재를 단정하지 않는다. 실패한 요청을 같은 인자로 반복하지 않고 오류가 가리키는 경로·범위·예산을 바꾼다. 조건이 있는 경로를 "항상"·"무조건"·"한 번도"로 단정하지 않는다.
<!-- /guidance-section: proof -->
