# 상태·책임·계약·수명

적용: 기능 설계, 구조 수정, 상태 불일치, 작업이 끝난 뒤 발생하는 오류.
근거와 버전: [설계 원칙 원문](sources.md#design). 아래 적용 기준은 조사에서 도출한 제안이다.

## 상태의 정본

| 구분 | 책임 |
| --- | --- |
| 정의 데이터 | 기본 능력치·설정·콘텐츠 ID를 정의 |
| 실행 상태 | 개체·매치의 현재 값을 확정 |
| 복제·예측·표시 | 확정값을 전달·추정·표현하며 보정과 폐기 조건을 가짐 |
| 영속 상태 | 저장·로드·이전의 경계와 성공 조건을 가짐 |

SSOT는 같은 사실의 확정 경로를 분명히 하는 원칙이다. 모든 값을 전역 객체에 모으는 조건이 아니다. 정의 데이터가 실행 상태를 초기화하는 지점과, 이후 변경 권한을 함께 찾는다.

팀 값과 멤버 목록처럼 같은 사실을 여러 형태로 보관한다면 한 변경 경로에서 함께 갱신하거나 하나를 파생한다. 두 저장소가 독립적으로 옳다고 판단하게 두지 않는다.

## SOLID를 판단에 사용하기

| 원칙 | 적용할 질문 | 과도해지는 경우 |
| --- | --- | --- |
| SRP | 같은 변경 이유가 모여 있는가? | 메서드마다 클래스를 만듦 |
| OCP | 반복되는 확장 지점이 실제로 있는가? | 예상만으로 확장 계층을 만듦 |
| LSP | 대체 구현도 입력·결과·실패·불변 조건을 유지하는가? | 타입 일치만 확인 |
| ISP | 소비자가 쓰는 기능만 의존하는가? | 모든 기능을 한 인터페이스에 넣음 |
| DIP | 핵심 규칙이 UI·저장소·전송 상세에 묶였는가? | 모든 클래스에 인터페이스와 컨테이너를 추가 |

DRY는 함께 바뀌는 규칙의 중복을 줄인다. 모양이 비슷해도 변경 이유가 다르면 분리를 유지할 수 있다. KISS·YAGNI는 현재 요구를 만족하는 단순한 형태를 선택하는 기준이다.

## 변경 경로와 수명

- 계약에는 유효한 입력, 결과, 실패, 부분 성공, 중복 요청의 의미가 포함된다.
- “이미 사망함”과 “이번 요청으로 사망함”을 구분한다. 보상·점수·예약은 필요한 전이에서만 발생시킨다.
- 사망·취소·매치 종료 뒤 늦은 타이머·비동기 결과가 상태를 되살리지 않도록 적용 조건과 정리 책임을 둔다.
- 동시에 존재할 수 있는 작업은 개체·요청별 수명을 갖게 한다. 전역 핸들 하나로 여러 작업을 덮어쓰지 않는다.
- 생성·로드·스폰 같은 실패 가능한 단계와 성공 상태 확정의 순서를 정한다. 중간 실패 시 기존 상태 보존·복구·재시도 가능성을 설명한다.
- 등록한 입력·이벤트·팀 멤버·작업은 누가 언제 해제하는지 연결한다. 객체, 활성화, 연결, Scene/World, 매치의 수명은 따로 본다.

## 패턴은 해결할 문제가 있을 때 선택

| 문제 | 후보 | 단순한 형태와 비용 |
| --- | --- | --- |
| 실제 교체되는 판정·전략 | Strategy | 함수·기존 컴포넌트로 충분한지 먼저 판단 |
| 허용 동작과 진입·종료가 상태별로 다름 | State/FSM | 전이 함수부터 시작; 독립 상태를 거대 enum에 모두 합치지 않음 |
| 같은 사실을 UI·음향 등이 관찰 | Observer | 구독 수명·재진입 책임이 추가됨 |
| 예약·기록·재실행할 입력 | Command | 단순 호출의 객체화 비용과 재실행 효과를 구분 |
| 반복되는 생성·초기화 규칙 | Factory/Composition Root | 엔진 생성 경로와 정리 책임을 재사용 |
| 독립 기능의 조합 | Component | 상호 내부 상태 변경과 순환 의존성을 피함 |
| 측정된 생성·폐기 비용 | Pool | 반환 시 상태·구독·작업 초기화가 필요 |
| 복잡한 UI와 게임 규칙 분리 | MVP/MVVM | 표시 계층에 확정 상태를 중복 소유시키지 않음 |

클래스 수, Singleton 유무, 인터페이스 수로 품질을 판정하지 않는다. 패턴 없는 코드의 계약이 명확하면 유지한다.
