# 비율 기반 컨텍스트 예산 — 1단계 구현 기록

- 날짜: 2026-11-10
- 작업 브랜치: `claude/harness-compactor-contract-audit-4fb294`
- 이어받은 기준 커밋: `0c2eb26`
- 관련 계획: [수정 계획](Harness_Editor_Authoring_And_Context_Revised_Plan_20261110.md)
- 상태: 플러그인 구현 및 자동 테스트 확인. 실제 LM Studio 실행·설치·병합은 별도이며, 계획의 모든 인수 조건을 완료했다는 뜻은 아니다.

## 구현 범위

기존 세 커밋 `b0b0821`, `eda8a06`, `0c2eb26`의 1단계 구현을 확인하고, 중단된 전체 테스트와 구현 기록을 이어서 수행했다. 이번 보완은 명시적 이어쓰기 한도의 보존 및 해당 호출 경로의 회귀 테스트다. 게임 프로젝트나 Unity Bridge, Unreal exporter는 수정하지 않았다.

| 항목 | 구현된 동작 |
|---|---|
| 설정 호환 | UI는 `legacy` / `percentage`를 선택한다. 기존 Auto/Fixed는 내부의 `legacy_auto` / `absolute`로 유지한다. 기본 선택은 legacy다. |
| 비율의 분모 | 모델에서 읽은 로드된 컨텍스트 길이 C. 조회 실패 시 설정된 대체 길이를 사용하고 `configured_fallback`을 기록한다. GPU 메모리 용량이나 모델의 이론상 최대 길이를 분모로 삼지 않는다. |
| 초기값 | 압축 목표 55%, 시작 75%, 출력 10%, 안전 여유 2%, 출력 상한 16,384토큰. |
| 실행별 계산 | `sessionBudgetConfig`가 모델 확인 후 한 번 계산하고, 기존 호출부가 읽는 유효 설정의 출력 예약과 안전 여유를 바꾼다. 저장 설정 자체는 바꾸지 않는다. |
| 실제 압축 경계 | `BudgetBroker`가 도구 결과 공간, 후속 요청 공간, 필수 입력을 고려해 목표와 시작점을 조정한다. |
| 압축 판정 | percentage에서는 기존 남은 토큰 임계값을 중복 트리거로 사용하지 않는다. 정확한 계측에서는 high와 다음 동작의 수용 가능 여부로 판단한다. 부정확한 계측의 메시지 수 기준은 유지한다. |
| 압축 후 지침 복귀 | 크기를 알고 있는 지침이 다시 들어올 공간을 미리 예약한다. 예약은 필수 입력 위 가용 공간의 절반 이하로 제한한다. |
| 계측 | `context_budget`, 적용 목표, 목표 초과 사유, 실행 중 C 변경, 필수 system 구간의 구성별 크기를 기록한다. 기존 모드에서는 percentage 예상값도 제공한다. |

목표·시작·출력·여유는 각각 C를 기준으로 한다. 서로 더해서 100%로 만드는 구성비 설정이 아니다. 출력 최소값과 최대값, 도구 결과 공간, 필수 입력 때문에 실제 값은 요청한 비율과 달라질 수 있다.

## 이번에 수정한 경계값

기존 `readConfig`는 이어쓰기 한도 0을 일반 출력 예약값으로 치환했다. 이후 `applySessionBudget`는 두 값이 같은지만 보고 자동값이라고 판단했다. 사용자가 두 설정을 모두 8,192로 명시한 경우에도 이 조건에 걸렸다.

- C=32,768: 명시적 한도 8,192가 4,096으로 바뀌었다. 실제 출력 호출은 원래도 일반 출력 예약에 의해 4,096으로 제한되므로 이 사례만으로 출력 초과를 주장하지 않는다.
- C=131,072: 명시적 한도 8,192가 13,107로 늘어나 사용자가 지정한 이어쓰기 한도를 넘을 수 있었다.
- 보완: `readConfig`가 `outputRecoveryFollowsReserve`에 원래 설정이 0이었는지 보존한다. 세션 계산은 이 플래그만 사용한다. `DeliveryController`의 실제 호출 상한 계산은 그대로 재사용한다.

변경 전 경계값 테스트가 실패하는 것을 확인한 뒤 수정했다. 근거 기록은 [JSON](evidence/harness-context-stage1-continuation-20261110.json)에 있다. JSON 검사 결과는 기록 형식의 일관성만 뜻하며, 동작 확인 근거는 소스와 테스트 결과다.

## 확인 결과

| 검사 | 결과 |
|---|---|
| 이어받은 구현 기준선 | 플러그인 테스트 1,378개 통과 |
| 보완 후 비율 예산 전용 테스트 | 14개 통과 |
| 보완 후 전체 플러그인 테스트 | 1,381개 통과, 실패·건너뜀 0개 |
| TypeScript 빌드 | 성공 |
| 생성물 검사 | design guidance, tool contract, Unity tool contract, runtime identity의 `--check` 4종 성공 |
| diff 공백 오류 | `git diff --check` 성공 |

추가한 호출 경로 테스트는 실제 `handlePredictionLoop`에 가짜 모델과 controller를 연결한다. 설치된 LM Studio나 실제 모델을 실행한 결과는 아니다.

- 일반 생성: C=32,768에서 출력 예약 4,096을 호출 옵션에 적용한다.
- 보고서 이어쓰기: C=131,072에서 첫 출력은 13,107이다. 명시적 이어쓰기 한도 8,192는 유지하고, 0이면 13,107을 따른다. 이어쓰기 호출에는 도구가 없다.
- 추론 복구: C=131,072에서 13,107로 시작하고, 공간이 충분한 한 번의 복구는 26,214를 사용한다. 별도 보고서 이어쓰기 한도 256을 추론 복구에 적용하지 않는다.
- 기존 전용 테스트는 다섯 가지 C, 기존 모드 호환, fallback, 비율 정규화, 필수 입력 초과, 지침 예약을 다룬다.

처음 `npm test`는 하위 cmd 프로세스에서 npm을 찾지 못해 시작되지 않았다. 현재 프로세스의 PATH를 Node·Windows·Git 경로로 짧게 지정한 뒤 동일 npm 빌드/테스트 경로가 실행됐다. 시스템 설정이나 저장소 스크립트는 이 문제 때문에 변경하지 않았다. 보완 과정에서는 새 테스트가 최초 조사 호출에도 도구가 없다고 잘못 가정하여 한 번 실패했고, 도구가 없어야 하는 이어쓰기 호출만 검사하도록 수정했다.

## 남은 인수 조건과 제한

1. C=32,768의 실제 추론 모델에서 최종 보고가 잘리지 않는지 확인해야 한다. 자동 테스트는 품질·지연·실제 출력 길이를 증명하지 않는다.
2. 수정 계획에서 요구한 bounded 최종 보고 및 조사 복구 각각의 percentage 전용 handler 시나리오는 이번에 추가하지 않았다. 기존 전체 회귀와 공통 유효 설정 전달이 확인됐지만, 이를 해당 모드 조합의 직접 실행 확인으로 확대하지 않는다.
3. 실행 중 C 변경은 계측 필드와 기존 안전한 호출 예산을 사용한다. percentage 모드의 모델 재로드를 실제 실행으로 확인해야 한다. 출력 예약은 다음 실행에서 다시 계산된다.
4. 알려진 지침 크기를 예약해도, 크기를 아직 모르는 선택 자료가 복귀하면 low를 넘을 수 있다. 현재 구현은 이를 `optional_material_after_compaction`으로 구분하며 무조건 목표를 만족했다고 보고하지 않는다. 모든 선택 자료에 low 입장 제한을 적용한 구현은 아니다.
5. 설정 화면의 동적 토큰 환산 표시 및 실제 UI 조작은 확인하지 않았다. 현재 적용값은 debug 계측에서 확인한다.
6. Unity/Unreal provider 테스트, 에디터 저장·재로드, 실제 모델 전후 평가는 이번 플러그인 변경의 실행 검증에 포함하지 않았다.

따라서 1단계의 코드와 자동 회귀 정리는 끝났지만, 실제 모델 검증을 포함한 단계 전체 승인 상태는 남아 있다. 이후 2단계는 상위 저장소 규칙 조회와 적용 범위·출처 보존이다. 3~6단계의 검토 기록, Unity/Unreal 관찰, 쓰기 사전 검사는 아직 이 변경에 포함되지 않는다.

## 전달 및 되돌리기

이 브랜치의 로컬 변경을 검토 대상으로 사용한다. Develop 병합, 원격 push, 플러그인 설치 및 LM Studio 재시작은 수행하지 않았다. 비율 동작은 `Context budget = Percentage of loaded context`에서 선택하며, `Legacy (token settings)`로 기존 예산 방식을 사용할 수 있다. 새 빌드를 만들었다는 사실만으로 설치된 앱의 동작이 바뀌지는 않는다.
