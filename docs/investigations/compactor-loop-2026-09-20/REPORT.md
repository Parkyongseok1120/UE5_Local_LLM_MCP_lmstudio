# LM Studio 반복 탐색 조사 및 수정 결과

조사 및 수정일: 2026-09-20. 원본 실패 기록을 보존한 뒤 같은 MCP 결과를 수정 코드로 재생하여 데이터 경로를 비교했다.

## 결론과 증명 범위

이 사례에는 모델의 검토 근거를 반복해서 지우는 실제 결함이 있다. **MCP 결과 포장 해석 누락 → 관찰 메타데이터 추출 실패 → soft 압축에서도 최신 도구 한 묶음만 보존 → 예전에 읽은 본문과 읽었다는 근거가 함께 사라짐**이 확인됐다. 별도로 화면용 본문을 모델 이력에도 재사용하여 같은 사용자 요청 안의 생각 내용이 다음 호출에서 사라진다.

이 결함들과 실제 재탐색의 시간 순서는 원본 대화에서 확인했다. 포장 누락과 메시지 변환의 정보 손실은 대조 실험으로 재현했다. 다만 실제 Qwen을 수정 전후로 전체 요청이 끝날 때까지 반복 실행한 실험은 하지 않았다. 따라서 모든 반복의 유일한 원인, 수정 후 반드시 완료, 개선 배수는 주장하지 않는다. 수정 후 실제 완료 검증은 계획의 필수 종료 조건이다.

앞서 제시한 “Git 도구 부재가 근본 원인”, “inject-full-content이므로 압축 없음”, “12회면 충분”, “4~8회로 끝날 것”은 입증되지 않았거나 원본 기록과 반대다. 이 계획의 근거로 사용하지 않는다.

## 확인한 결함

### 1. 실제 MCP 결과 포장을 해석하지 못함 — 데이터 손실 재현 완료

`src/compaction-tool-memory.js:185`의 parseToolResult는 JSON.parse 결과가 업무 결과 객체라고 가정한다. 실제 LM Studio 결과는 다음 구조다.

```json
[{"type":"text","text":"{\"status\":\"observed\",\"path\":\"...\",\"hash\":\"...\"}"}]
```

외부 배열에는 path/hash 필드가 없으므로 결과가 `tool result contained no retained factual fields`로 바뀐다. 문법 오류조차 아니어서 성공한 관찰이 조용히 없어지는 형태다.

실제 결과 51개를 그대로 입력하면 로컬 및 설치본 모두 51개 전체에서 이 현상이 발생한다. 같은 입력의 단일 text 포장만 풀면 path 42개, sha256 36개가 추출된다. 실제 두 파일의 첫 읽기를 압축하는 대조 실험에서 포장 입력은 0개 파일, 포장을 푼 입력은 2개 파일과 정확한 1~200 범위를 남긴다. 기록된 압축 시점으로 반복 재생하면 최종 0개 대 6개 파일이 된다.

반대 근거/한계: 실시간 모델은 압축 전 원본 도구 결과를 볼 수 있었다. 문제가 모든 읽기의 원문 전달 실패는 아니다. 포장을 풀어도 오래된 소스 본문 자체를 저장하는 정책은 없으므로, 파서만 고쳐도 전체 검토가 끝난다고 주장하지 않는다.

### 2. soft 압축의 현재 턴 보존 정책이 최근 한 묶음으로 축소됨 — 소스 및 실제 기록 일치

`src/prediction-loop.ts:585`에서 일반 압축 후 여전히 soft 기준에 걸리면 `maxCurrentTurnMessages: 2`로 다시 압축한다. 이 값은 사용자 요청을 진행 중이어도 최신 도구 한 묶음만 남기게 한다. 결과 1의 파싱 실패와 결합하면 그 이전 소스 본문뿐 아니라 읽은 파일/범위 기록까지 사라진다.

반대 근거/한계: 최신 미독해 도구 결과를 보존하는 기능과 요청/결과 짝은 정상이다. PDF와 도구 정의도 토큰을 차지하므로 과거 전체를 영구 보존할 수는 없다. 결함은 메모리 부족 자체가 아니라 조기 압축 시 증거를 잃는 방식과 아주 작은 고정 보존량이다.

### 3. GUI 표시용 메시지를 모델 이력에도 사용함 — 실제 프롬프트 변환 확인

`src/prediction-stream.ts:126`은 생각을 제외한 표시용 텍스트를 반환한다. `src/prediction-loop.ts:698`에서 메시지 텍스트를 그것으로 교체하고 `:775`에서 workingHistory에도 추가한다. GUI 생각 블록은 includeInContext=false다.

SDK 1.5.0의 기본 act 루프는 원문 contentArray를 assistant 메시지에 이어 붙인다. 로드된 실제 qwen/qwen3.8-27b의 applyPromptTemplate로 대조하면 원문에서는 이전 생각의 sentinel이 <think>에 남고, 표시용 본문에서는 빈 <think>가 된다. 도구 결과 sentinel은 양쪽 모두 남는다. 생성은 하지 않았으며 템플릿 변환만 검사했다. 진단 핸들에는 SDK tokenSource와 같은 방식으로 저장된 per-chat 설정을 적용했다.

반대 근거/한계: 생각을 항상 재주입해야 모든 모델의 추론 품질이 향상된다는 일반 주장은 아니다. 동일 턴 내 Qwen 기본 경로와의 불필요한 차이를 증명한 것이다. 이 조치 하나로 실제 반복이 해소되는지는 전체 실행 대조가 필요하다.

## 배제하거나 보류한 설명

- Git 도구 부재: 변경분 검토를 비효율적으로 만들 수 있지만, 위 정보 손실을 설명하지 못한다. 근본 수정과 분리한다.
- 파일이 계속 변경되어 재조회: 반복 읽기의 hash가 동일하므로 해당 파일에 대해서 배제한다.
- PDF 미전달: 원본 첨부와 전처리 본문이 존재하므로 배제한다. 전처리 본문이 큰 고정 비용을 만드는 문제는 별도다.
- 압축 미발생: 20개 실제 debug 기록으로 배제한다.
- SDK가 도구 결과를 전혀 전달하지 않음: 51개 결과가 저장되어 있고 샘플 요청/결과 ID와 재주입이 유지된다. 과거 결과의 압축 이후 소실과 구분한다.
- 종료한 답변을 플러그인이 무조건 재호출: 현재 소스는 tool 결과 경계에서만 재호출한다. 이 기록은 최종 답변 없이 도구 요청이 계속 나오는 경우다. 다른 종료 오류 가능성까지 포괄적으로 배제하지는 않는다.
- 모델 자체 반복 성향/잘못된 CS0162 판단: 독립적으로 남을 수 있다. harness 결함을 고친 다음 동일 모델/동일 설정 대조로 분리해야 한다.
- 읽기 범위 메모가 이미 이해한 코드 의미를 증명: 그렇지 않다. 범위 메타데이터는 원문이나 모델 판단의 대체재가 아니다.

## 수정 계획

1. **실제 MCP 응답 형태를 정규화한다.** 기존 parseToolResult 앞에서 직접 객체, MCP 단일/복수 text content, 지원할 structuredContent 형식을 명시적으로 해석한다. 알려진 포장만 제한된 깊이/크기로 푼다. 여러 결과를 서로 다른 프로젝트 근거로 합치지 않는다. 포장을 푼 뒤 기존 제어 필드 및 receipt 제거, 프로젝트/파일/hash/범위 검증을 그대로 적용한다. 오류와 이해하지 못한 응답을 '사실 없음'과 구분해 진단에 남긴다.
2. **현재 턴의 모델 이력과 GUI 이력을 분리한다.** workingHistory는 SDK assistant 원문과 tool 구조를 보존한다. GUI는 기존 생각/본문 스트리밍을 사용한다. 비공개 continuity footer만 정해진 파서로 분리한다. 판단을 system 사실로 승격하거나 별도 LLM으로 요약하지 않는다. 새 사용자 턴/영속 메모의 생각 보존은 별도 정책이며 무조건 전체 저장하지 않는다.
3. **soft 압축의 2개 메시지 고정 축소를 토큰 예산에 맞는 보존으로 바꾼다.** 기존 정확한 토큰 측정과 완전한 요청/결과 그룹 처리를 재사용한다. 최신 미독해 결과를 항상 포함하고, 현재 작업의 완전한 교환 묶음을 예산 안에서 더 보존한다. 목표 입력 크기와 재압축 여유를 사용하여 한 번 읽을 때마다 대규모 삭제가 반복되지 않게 한다. 12회 제한, 강제 최종 답변, 서버의 다음 행동 선택은 도입하지 않는다.
4. **첨부와 사용자 요청의 경계를 검증하고 필요한 최소 조정을 한다.** 현재 RAG가 이미 합친 42,432자를 compactor가 원래 사용자 요청처럼 취급한다. 기존 read_attached_document와 파일 식별자를 재사용할 수 있는 구조적 전처리 경로를 먼저 확인한다. SDK pullHistory에는 원본/전처리 이력 선택 인자가 없으므로, 문자열 패턴으로 PDF를 잘라내거나 첨부를 추측해 분리하지 않는다. 1~3 수정 후 같은 PDF로 충분한 작업 근거가 유지되면 첨부 경로 재설계는 미룬다. 부족하다면 전처리 단계에서 원래 요청과 첨부 출처를 별도로 전달하는 변경을 추가한다.
5. **실제 완료까지 비교하고 배포한다.** 동일 모델, 템플릿, PDF, 프로젝트 스냅샷, 도구 목록, sampling 설정으로 수정 전후를 비교한다. 파서 수정만/이력 수정만/보존 정책까지 적용한 조건을 구분하여 효과를 확인한다. 시간/출력 제한은 실험 중단 장치로만 사용하며 정상 완료로 계산하지 않는다. 사용자 GUI에서 본문 완료와 입력 가능 상태도 확인한 다음 버전·패키징·업데이트를 진행한다.

## 구현 및 재생 결과

계획 1~3을 다음과 같이 구현했다.

- `parseToolResult` 앞에 제한된 MCP 결과 디코더를 추가했다. 직접 객체, 단일 text content 배열, `structuredContent`, 단일 text `content` 객체만 허용하며 복수 블록·손상 JSON·과대 입력은 합치지 않고 버린다. 디코딩 뒤에는 기존 receipt 제거와 프로젝트·파일 사실 검증을 그대로 거친다.
- GUI 표시 메시지와 다음 모델 호출용 이력을 분리했다. 화면에는 생각과 본문을 기존 블록으로 나눠 표시하고, 모델 이력에는 SDK가 만든 assistant 원문을 유지하되 비공개 continuity footer만 제거한다.
- soft 압축은 최신 두 메시지로 바로 축소하지 않는다. 목표 잔여 토큰을 만족하는 가장 큰 완전한 assistant/tool 교환 묶음을 이진 탐색으로 선택한다. hard 경로와 토큰 측정이 불가능한 fallback의 최소 보존 동작은 유지한다.
- 파일 메모에는 동일 hash에서 관찰한 줄 범위를 합쳐 남긴다. 원본 파일 본문은 체크포인트에 복제하지 않는다.

수정 후 원본 대화의 51개 실제 MCP 결과를 그대로 재생한 결과:

- 래핑된 결과와 비교용 직접 JSON 결과에서 `path` 추출 수가 각각 42개로 같았다.
- `sha256` 추출 수도 각각 36개로 같았다.
- 첫 두 파일 압축 대조에서 두 경로 모두 2개 파일과 각 1~200줄 범위를 남겼다.
- 기록된 20개 압축 시점을 연속 재생한 최종 메모에는 6개 파일이 남았다. `StoryScriptRunner.cs`는 1~719줄, `StoryCraftGate.cs`는 1~347줄로 합쳐졌다.
- 전체 도구 결과 본문은 체크포인트에 복제되지 않았다.
- 압축기 테스트 158개와 Unity MCP 테스트 22개 중 실행 가능한 20개가 통과했다. Unity MCP의 외부 Roslyn 환경 테스트 2개는 기존 조건대로 건너뛰었다.

이 재생은 수정된 파서와 메모리 보존 경로를 증명한다. 실제 Qwen이 동일한 PDF 검토를 최종 답변까지 완료한다는 보장은 아니므로, 설치본으로 동일 작업을 실행하는 GUI 검증을 별도 종료 조건으로 유지한다.

필수 검증:

- 실제 포장 fixture가 plain JSON fixture와 같은 허용 사실을 남기는지. 복수 content, 오류, 손상 JSON, 대형 결과, 다른 프로젝트, 쓰기 receipt도 검증한다.
- 같은 사용자 턴의 다음 렌더링된 프롬프트에 이전 assistant 의미와 tool ID/결과가 남는지. GUI는 생각과 본문을 중복하지 않는지.
- 첨부 포함 압박 조건에서도 최신 도구 한 묶음 외의 검토 근거가 예산 내에서 유지되는지. 필요한 원문이 없어졌는데 메타데이터만으로 검토 완료했다고 주장하지 않는지.
- 동일 hash의 범위 재조회 비율, 새로 읽은 범위, 압축 횟수, 최종 답변 유무, 중단 사유를 기록한다. 지표 계산은 deterministic하게 수행한다.
- 실제 사용자 요청에서 검토 결과가 나오는지 확인한다. 파서 테스트 통과만으로 '무한 반복 해결' 판정을 내리지 않는다.

```powershell
node docs/investigations/compactor-loop-2026-09-20/replay.cjs <LMSTUDIO_HOME>/conversations/84/1789836297694.conversation.json --live-template --output docs/investigations/compactor-loop-2026-09-20/results-after-fix.json
```

재생은 실제 요청/결과와 실제 압축 시점을 사용하되 사용자 텍스트를 짧은 대체 문구로 사용한다. 원본 전체 프롬프트 재생이라고 오해하지 말아야 한다. 목적은 동일 결과의 포장 유무만 바꾼 데이터 경로 대조다.
