# 중단 후 다음 턴의 근거 복원 수정

## 확인한 문제

2026-09-25의 중단된 조사와 후속 보고 요청을 읽기 전용으로 재구성했다.
사용자 메시지에 서명된 이전 대화 fingerprint는 모두 일치했다. 저장된 작업 창의
digest와 32개 아카이브 참조의 기록 해시·본문 해시도 정상이었다. 새 복원 진단으로
후속 입력을 검사한 결과는 `source_prefix_mismatch`였다. 원본 대화나 프로젝트의
파일 내용은 이 문서에 포함하지 않는다.

기존 저장 경계는 SDK의 캡처 메시지를 `visibleHistory`에 추가해서 만들었다.
화면에는 스트리밍 설명, 개별 도구 요청, 도구 결과가 서로 다른 블록으로 저장된다.
따라서 여러 요청을 담은 SDK 메시지와 다음 턴의 호스트 기록은 동일한 배열이 아니다.
또한 저장은 호출 직전에만 이루어져 중단 시점의 반환 결과와 미완성 계획을 구분한
종료 스냅샷이 없었다.

의미 요약은 해당 실행에서 시간 초과했다. 이는 복원 실패와 구분해야 한다.
파일 본문은 아카이브에 남아 있었으며, 로그만으로 삭제됐다고 판단할 수 없다.

## 책임과 수명

| 소유자 | 책임 | 경계 및 수명 |
| --- | --- | --- |
| `VisibleHistoryRecorder` | 실제 생성한 화면 블록을 기록하고 원본 대화 prefix를 구성 | 한 실행. thinking 블록 제외. 화면의 중단된 텍스트는 원본 경계에만 포함 |
| `RoundTransaction` | 반환된 도구 결과와 완료한 계획을 구분 | 한 모델 라운드. 취소된 prose는 작업 창에 승격하지 않음 |
| `WorkingContext.commit` | 정확히 측정된 호출 입력을 저장 | 현재 실행의 측정이 성공한 뒤에만 저장 |
| `WorkingContext.seal` | 마지막 반환 결과와 승인된 계획으로 종료 스냅샷 작성 | 현재 실행에서 commit한 창만 확장. 성공 뒤 재진입 거부 |
| `WorkingContext.restore` | 서명된 대화 범위 안에서 prefix·참조·무결성 검사 | 다음 실행. 복원 성공은 모델 호출 허가가 아님 |
| `ContextManager` | 현재 모델·도구·출력 예산으로 입력 재측정 | 매 호출. 종료 스냅샷의 과거 측정치를 재사용하지 않음 |
| `EvidenceArchive` | 본문 보관과 정확한 버전의 과거 근거 재조회 | 기존 범위·TTL·용량 정책 유지. 새 파일 읽기나 변경 권한을 부여하지 않음 |
| prediction handler의 `using toolSession` | 도구 세션 해제 | 초기화 오류, 정상 종료, 취소, 종료 저장 중 오류 모두 해제 |

요청-결과 짝짓기는 호스트가 나눠 저장한 연속 assistant 요청도 같은 batch로 처리한다.
중복 ID, 일부 결과 반환 뒤 새 요청, 사용자 턴을 넘는 미완료 batch는 여전히 거부한다.
응급 복구는 먼저 도구 목록을 줄여 본문을 유지할 수 있는지 측정하고, 실제 checkpoint가
필요하면 아카이브 투영을 거쳐 다시 측정한다.

종료 스냅샷은 `measurement: null`, `measurementSubject: terminal_unmeasured`,
`remeasureRequired: true`로 저장한다. 기존 schema 1의 범위 및 prefix 검사를 유지한다.
이전 버전에서 이미 잘못 저장한 prefix를 강제로 신뢰하거나 기존 대화를 수정하지 않는다.
저장 실패 시 이전 원자적 창을 유지하고, 다음 턴은 검증 가능한 창 또는 원래 대화로 돌아간다.

## 검증

검증 결과: 후속 보고 실패 수정까지 포함하여 `npm test` 376개 통과.
그 뒤 설치 진단에서 발견한 CLI entry 형식 오인 수정은 관련 상태 검사 테스트
5개 재실행 통과. 근거 JSON 검사, 저장소 인코딩 검사, `git diff --check` 통과.

- 실제 호스트 형태로 재구성한 메시지를 사용하여 다중 요청 → 반환 결과 → 사용자 취소 → 보고 전용 다음 턴을 검사.
- 마지막 반환 본문 보존, 미완료 prose·reasoning·receipt·cursor 배제, 다음 실행의 정확한 입력 측정 확인.
- 요약 시간 초과 후 프로세스 수준의 새 WorkingContext에서 보관 본문 재조회 확인.
- 변경된 prefix, 잘못된 범위·분기, 손상·만료된 참조 거부 및 저장 실패 시 기존 파일 유지 확인.
- 종료 뒤 중복 seal/commit 차단, 측정 전 seal 차단, 초기화 오류 시 도구 세션 해제 확인.

중단 후 다음 턴 복원은 자동 회귀 테스트와 기존 실행 기록의 오프라인 재현으로 검증했다.
아래의 실제 모델 재현은 보고 생성에 한정하며, GUI의 중단→복원 전체 경로 검증과 다르다.
임의 길이의 모든 코드가 항상 모델 입력에 들어가거나 요약 모델의 내용 이해를 보장하지 않는다.
과거 전체 본문은 기존 재조회 도구 및 보관 정책을 따른다.

## 후속 재시도에서 확인한 보고 실패

같은 대화의 두 번째 응답은 실행 지문이 수정 전 설치본과 같았다. 앞선 저장소 수정이
실제 실행에 반영된 사례로 볼 수 없다. 별도로 다음 결함을 확인했다.

1. 세 요청 중 두 파일의 1–200행 읽기는 성공하고 마지막 요청만 공유 batch 예산에서 거부됐다.
2. `progressed=true`, 성공 관측 2개인데 `errorCount=1`만으로 복구 전체를 소진 처리했다.
3. 일반 모드의 자동 복구 보고가 bounded audit의 4096토큰·70초 제한을 상속했다.
   실제로 약 70초 뒤 내부 시간 초과했고, visible 출력은 0자였다. `userStopped`라는
   모델 통계와 달리 호스트의 `phaseTimedOut=true`가 종료 원인을 보여준다.
4. 대체 보고는 `workspace_file_observation`을 지원하지 않아 성공 근거 2개를 누락했다.

수정 후 `RecoveryCoordinator`는 오류가 섞여도 관측 진행이 있으면 다음 소비 기회를 준다.
`DeliveryController.limits`가 일반 모드, 명시적 bounded audit, output recovery의 출력과
시간 정책을 한 곳에서 결정한다. 일반 모드의 자동 복구 보고는 기존 일반 출력 한도와
사용자 취소를 따르며, 명시적 제한 모드의 제한은 유지한다.

대체 보고는 반환된 파일의 줄/바이트 범위와 제한된 본문 발췌를 보여주고, 시간 초과와
빈 응답의 원인을 구분한다. 진행 중·상태 미상의 파일 결과를 성공 근거로 승격하지 않는다.
실제 후속 로그의 결과 3개를 새 보고 함수로 재생했을 때 성공 근거 2개, 오류 1개,
줄 범위와 본문 발췌가 포함되는 것을 확인했다.

## 실제 모델 재현 및 설치

현재 로드된 `swift-qwen3.8-27b` 모델과 SDK 1.5.0에 실제 반환 결과 3개를 재생했다.
사용자 대화에는 메시지를 추가하지 않았고 외부 도구 실행은 0회였다.
입력 6203토큰, 모델 컨텍스트 86272, 출력 한도 8192, 일반 보고의 별도 시간 제한 없음으로 실행했다.
약 189초 동안 실행되어 코드 내용에 대한 visible 보고 13539자를 생성했으나,
`maxPredictedTokensReached`로 종료됐다. 따라서 보고 생성은 확인했고 완결은 확인하지 못했다.
70초 강제 중단 해소가 출력 길이·모델 서술 품질까지 보장하지는 않는다.

`lms dev --install -y`와 설치본 SDK 패치를 실행했다. 기존 설치 코드는 로컬 임시 폴더에
백업했으며, 대화 및 GUI 예산 설정을 변경하는 통합 설치기는 실행하지 않았다.
설치본의 source 및 dist 지문이 검증한 작업본과 일치했고 production bundle에 수정 경로가 포함됐다.

- source SHA-256: `4627a718f63607c0230f224d1fe5b09ae8c42466086f011aabf34ca412d816fd`
- dist SHA-256: `04ef37ae60c28f2e96707289f628a5ab3cb2df0eb10a5f1b333c50c68a6cb258`

CLI가 생성하는 entry는 `withPromptPreprocessor: (preprocess) => ...` 형식이다.
상태 검사기는 저장소 entry의 메서드 형식만 인식했으므로 정상 설치를 실패로 오인했다.
두 형식을 인정하되 실제 host 등록 호출이 없으면 거부하도록 수정하고 회귀 테스트를 추가했다.
상태 검사의 파일 배치 검증은 GUI 런타임 활성화 증명이 아니다. 수정 후 GUI 대화 재실행은 미검증이다.
