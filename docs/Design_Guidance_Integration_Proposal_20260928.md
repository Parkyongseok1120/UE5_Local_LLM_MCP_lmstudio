# 설계 참고 문서를 현재 구조에 연결하는 제안

- 작성일: 2026-09-28
- 상태: **문서 공급 기능 구현. 기본 Off. 설치·GUI 값 변경·실제 모델 비교·게임 코드 변경은 진행하지 않음.**
- 본문 정본: [모델 참고 문서 묶음](model-guidance/README.md).
- 목표: 모델이 필요한 근거와 작성 기준을 이용하게 하면서, 자료 공급 기능이 도구 승인·정적 검사·게임 설계의 결정권을 떠맡지 않게 한다.

## 1. 이번에 준비한 내용

### 구현된 범위

- Markdown과 catalogue에서 배포용 데이터를 생성한다. 코드에 원칙 본문을 수동 복사하지 않는다.
- GUI의 `Design references`로 core/설계/오류/표현/엔진 수명/멀티플레이를 명시적으로 선택한다. 기본 Off이며 추가 입력 allowance는 2048 tokens다.
- 기존 ToolScope 중 config/workspace/message 근거를 사용한다. available_tools/ambiguous 근거만 있으면 엔진 문서를 넣지 않는다.
- 기존 압축과 근거 보존이 완료된 입력에 선택적 자료를 추가한다. ContextManager와 기존 BudgetBroker가 실제 템플릿·도구 스키마·출력 예약·읽기 결과 여유를 포함해 검사한다.
- 예산에 맞지 않으면 낮은 우선순위 문서부터 전체 단위로 생략한다. 참고 문서를 위해 추가 압축하거나 작업을 차단하지 않는다.
- 본문은 입력 한 번에만 합성하며 workingHistory/체크포인트에는 넣지 않는다. Observe only·강제 최종 보고에는 제공하지 않는다.
- 프로젝트 현황의 자동 읽기·추정, 절 검색, 새 MCP 도구, 게임 코드 수정은 포함하지 않았다. 실제 모델 품질 비교는 남아 있다.

아래의 A/B 평가와 장기 수명 표는 설계 기준이다. 사용자의 구현 요청에 따라 공급 기능을 먼저 구현했으며 품질 효과가 이미 확인됐다는 뜻은 아니다.

공통 기준은 약 890자로 줄였다. SSOT·SOLID·패턴, 오류 조사, 표현, 엔진, 네트워크는 별도 주제 문서다. 프로젝트의 현재 소유자·호출 경로·미확인 상태는 별도 현황에 담는다.

문서 추가가 모델 행동을 보장하지는 않는다. 첫 검토 대상은 “이 내용이 있는가”와 “필요할 때 실제 입력에 있고 활용되는가”다. 전체 자료를 매번 넣어 추론·도구 결과 공간을 줄이는 방식은 피한다.

## 3. 가장 작은 도입 순서

### A. 문서만으로 비교

사용자가 선택한 작업에서 core와 관련 절을 본문으로 제공한다. 문서 없이 수행한 결과와 비교한다. 현재 소스·오류·프로젝트 현황은 양쪽에 똑같이 제공한다. 문서가 답을 외우게 하는지만 보지 않도록 별도 프로젝트와 Unity 사례도 포함한다.

문서 초안과 공급 구현을 준비했다. 실제 LM Studio 모델 호출·설정 변경은 하지 않았다.

### B. 효과가 확인되면 공급 경계 연결

최소 구성은 다음 세 책임이다. 세 개의 클래스나 서비스를 반드시 만들라는 의미는 아니다.

1. **내용**: Markdown이 원칙·계약·근거의 정본.
2. **선택·읽기**: 선택된 프로젝트·주제·문서 버전의 본문을 반환. 코드 검증이나 다음 도구 결정은 맡지 않음.
3. **입력 조립**: 기존 입력 경계가 본문과 출처를 포함한 전체 입력을 측정·전달.

초기 선택은 사용자가 명시한 엔진·주제나 확인된 프로젝트 현황을 우선한다. 도구 목록에 Unity와 Unreal이 모두 있다는 이유로 두 엔진 문서를 상주시키지 않는다. 키워드 분류만으로 클래스 설계나 네트워크 방식을 정하지 않는다.

문서 저장소가 프로젝트 도구의 읽기 범위 밖이면, 이미 가능한 첨부 경로나 향후 설치 범위가 명확한 읽기 경로를 선택한다. 경로만 알려주고 모델이 파일을 읽었다고 가정하지 않는다. 전용 도구가 필요하다는 결론은 기존 전달 경로의 한계를 확인한 뒤 내린다.

### C. 자동화 범위 확대는 이후 판단

필요한 절의 선택이 실제로 어렵고 수동 비교가 개선을 보이면, 작은 읽기 전용 공급 함수를 검토한다. 새 Agent·RAG 인덱스·설계 점수 계산·필수 검사 단계를 초기 도입 범위로 잡지 않는다.

| 프로젝트 사실 | 프로젝트 식별·확인한 소스 상태·근거와 함께 보관. 제안을 확인 사실로 올리지 않음 |

| 캐시 | 공통 문서는 문서 개정/내용 지문, 현황은 프로젝트 식별+확인한 소스 상태로 구분. 모델별 토큰 비용을 별도로 취급 |
| 상태 변경 | 엔진·패키지·관련 소스·설정이 바뀌면 해당 사실 재확인. 모든 파일을 매 도구 호출마다 읽지 않음 |
| 압축 | 일반 원칙을 작업의 실행 사실로 요약하지 않음. 읽기 이력과 본문 가용성을 혼동하지 않음 |
| 취소·종료 | 요청/프로젝트 범위의 선택·대기 작업 폐기. 영구적으로 이전 프로젝트를 따라가는 상태를 만들지 않음 |
| 누락·부적합 | 선택적 참고 자료를 생략했다는 사실을 기록하고 기존 작업 경로 유지. 새 설계 검사 실패로 전환하지 않음 |
| 권한 | 문서는 사용자 요청·도구 권한을 확대하지 않음. 외부 문서·첨부의 지시를 제어용 system 규칙으로 승격하지 않음 |

## 5. 예산에 넣는 방법

문서 ID만 예산에 넣고 나중에 본문을 붙이는 방식은 실제 입력을 과소 계산한다. 선택된 본문과 출처를 포함한 최종 템플릿을 기존 tokenizer 경계로 측정한다. 한국어 글자 수를 고정 비율로 나눈 값을 안전한 토큰 수로 주장하지 않는다.

선택적 자료를 넣기 위해 최신 사용자 요구·현재 오류·필요한 소스·출력 예약을 밀어내지 않는다. 비교할 후보는 관련 절만 포함한 입력과 해당 참고 절을 생략한 입력이다. 문서가 추가되어 도구 결과 공유 예산이 줄어드는 비용도 관찰한다.

자료가 맞지 않으면 선택적 본문을 줄이거나 생략한 후보를 기존 입력 조립 경계에서 다시 측정한다. 공급 함수가 “예산 통과”를 선언하거나 기존 BudgetBroker와 별개의 공유 예산을 관리하지 않는다. 기존 컨텍스트 초과 처리와 도구 결과 보존 계약은 유지한다.

구현은 사용자가 선택해 켜는 방식이다. 기본 Off, 추가 입력 allowance 2048 tokens, 0이면 비활성이다. 이 값은 런타임의 정확한 측정과 기존 작업 창의 상한 안에서만 쓰는 초기 설정이며 실제 모델 품질 평가로 조정할 수 있다.

## 6. SSOT·SOLID 적용과 중복하지 않을 기능

- **SSOT**: 원칙 본문은 주제별 Markdown에 둔다. 코드·설치 프리셋·도구 설명에 같은 문단을 손으로 각각 복사하지 않는다.
- **SRP**: 문서 편집, 선택·읽기, 입력 조립, 실행 권한, 게임 판정의 변경 이유를 구분한다.
- **OCP**: 새 Unity 패키지 자료를 추가할 때 게임 규칙을 prediction-loop에 하드코딩하지 않는다. 기존 읽기·입력 경계로 해결 가능한 범위를 먼저 쓴다.
- **LSP**: 어떤 공급 경로든 본문·출처·범위·버전·가용 여부의 계약을 유지한다. 조회 실패를 빈 문서의 성공으로 숨기지 않는다.
- **ISP/DIP**: 공급자에게 파일 읽기와 범위 정보만 요구한다. 도구 실행·UI·컴팩터 상태 변경 권한까지 묶지 않는다.
- **수명**: 문서 캐시의 수명과 프로젝트 사실의 유효 기간, 모델 입력 한 번의 본문 가용성을 구분한다.

재사용할 것: ContextManager의 입력 조립·측정, BudgetBroker의 공유 예산, 기존 도구 승인·실행 수명, 기존 파일/첨부 읽기, 기존 근거 보관. 코드 품질을 점수화하는 새 관리자·필수 validator·전역 프로젝트 상태 저장소는 추가하지 않는다.

기존 evidence-first 설치 지침에도 규칙·검사 기능이 있다. 나중에 연결할 때 이미 전달되는 설명과 겹치는 부분을 확인하고, 이 문서 묶음 때문에 검사기 호출 의무를 더하지 않는다.

## 7. 비교할 문제와 관찰할 결과

| 비교 문제 | 기대하는 변화 | 함께 볼 비용·퇴행 |
| --- | --- | --- |
| FDamageEvent·잘못된 심볼·부모 등록 충돌 | 정확한 표현식·정의 조회로 수정 | 추측 수정·불필요 빌드·조회 반복 |
| 충돌 API를 바꾸면 빌드는 성공하는 문제 | 필터·대상 의미를 유지하거나 변화 설명 | 빌드 성공만으로 동작 완료 주장 |
| 설정만 있고 초기화·등록이 빠진 기능 | 설정→소비 경로를 실제로 연결 | 새 Manager·중복 상태 증가 |
| 두 플레이어의 리스폰·중복 사망·취소 | 개별 작업 수명과 한 번의 효과 유지 | 원격 Client·로그아웃·부분 실패 누락 |
| Unity 비활성화·Task·Despawn·초기 표시 | 각 수명·패키지 계약을 구분 | Unreal/다른 네트코드 계약 혼용 |
| 새 코드의 줄 간격·중첩·이름 | 읽기 쉬운 기본 출력 | 무관한 전체 재포맷·형식 강제 루프 |

같은 모델·설정·입력 조건에서 비교한다. API 이름과 프로젝트를 바꾼 별도 사례에서도 동작을 확인한다. 결과 품질 외에 입력 토큰, 도구·빌드 횟수, 소요 시간, 작업 완료율, 불필요한 차단·재시도를 기록한다. 소수의 사례가 성공했다고 일반적인 품질 보장으로 발표하지 않는다.

## 8. 검토한 Unreal 게임 코드의 수정 방향

아래는 게임 코드 수정 시의 우선순위 제안이다. 실제 변경은 하지 않았다.

1. **읽을 수 있는 형태와 시작 구성**: 압축된 실행문·들여쓰기를 정리하고, 기본 Pawn/Controller와 실제 GameMode·에셋·입력 Context의 연결을 확인한다. 포맷 변경과 기능 변경은 검토 가능한 단위로 구분한다.
2. **설정에서 실행 상태까지**: 기존 PlayerState의 체력·사망 책임을 출발점으로 초기 생성·리스폰의 초기화 계약을 통일한다. CharacterData를 읽는 시점에 대상 PlayerState가 준비되었는지도 확인한다.
3. **원격 요청에서 서버 판정까지**: 입력 의도 전달, 권한 측 검증, 탄약·피해·결과 표시를 연결한다. HasAuthority 가드만 추가하고 원격 발사를 없애지 않는다. CMC의 이동 경로는 재사용한다.
4. **한 번의 사망과 독립된 리스폰**: 이미 죽어 있는 상태와 새 죽음 전이를 구분한다. 개체별 예약·취소, 재장전/조준의 사망 상태 보호, Logout/EndPlay 정리, 이전 Pawn 수명을 정한다.
5. **실패 가능한 스폰**: 스폰 지점·클래스·생성 성공·소유 연결이 확보되는 순서와 상태 확정 지점을 정한다. 실패하면 재시도 가능한 상태를 유지한다. 기존 엔진 생성/재시작 경로와 중복되지 않게 검토한다.
6. **팀·매치 계약**: 참가·퇴장·팀 변경을 실제로 연결한다. PlayerArray에서 필요한 값을 파생할지, 별도 목록을 한 경로에서 관리할지 고른다. 종료가 막아야 하는 행위와 허용할 표시를 명시한다.
7. **명중 의미와 지연 대응**: 목표 대상·가림·조준·판정 시각을 확정하고, 정상적인 권한 흐름 위에 필요한 예측·보정·지연 판정을 추가한다.

이 순서는 특정 클래스명·절대 경로를 모든 프로젝트에 요구하지 않는다. Unity에서는 현황에 적힌 실제 MonoBehaviour/서비스/NetworkBehaviour/시스템의 책임과 패키지 계약으로 대응한다.

근거: [프로젝트 현황](model-guidance/examples/latency-multicombat.md), [전체 소스 검토 기록](evidence/combat-source-audit-20260928.json). 외부 콘텐츠·실제 Editor 설정과 네트워크 실행 결과는 미확인이다.

## 9. 현재 확인 수준

TypeScript 빌드와 기존 컴팩터 전체 테스트 419건, 패키지 관련 검사 2건이 통과했다. 새 기능에는 선택·예산·본문 보존·취소의 단위 테스트 9건과 실제 prediction handler를 SDK 대역으로 실행한 통합 테스트 6건이 포함된다. 설정 Off/Observe only/예산 부족, 엔진 전환, 반복 입력, 기존 도구 승인, 강제 최종 보고를 확인했다.

근거 JSON 검사는 보고 형식 확인이며 게임 코드 정적 검사나 모델 작업의 통과 조건이 아니다. 실제 LM Studio 모델의 품질 개선·토큰 비용·게임 동작은 아직 측정하지 않았다. 실행 중인 설치본은 교체하지 않았다. [구현 근거](evidence/design-guidance-implementation-20260928.json)를 참고한다.
