# Unity MCP 파일 탐색 최소 개선 계획

상태: 구현 및 자동 검사 완료 — 2026-09-18. 실제 Unity Editor에서 모델의 탐색 선택을 검증한 결과는 아니다.

## 목표와 책임

모델이 조회 경로, 검색 조건, 추가 조사와 종료를 결정한다. 서버는 요청받은 범위에 정해진 필터와 자원 제한을 적용하고 관찰 결과를 반환한다. 구조 개요는 전체 파일 수집을 완료 조건으로 삼지 않는다.

이번 범위는 비재귀 폴더 조회 하나, 기존 검색의 확장자 필터, 응답 의미와 커서 경계 보강이다. 자동 조사, 관련 파일 추천, 중요도 정렬, 파일 역할 추정, 전체 프로젝트 인덱스, 파일 종류별 자동 할당은 범위에 포함하지 않는다.

## 확인한 기존 구조

- `lmstudio-unity-mcp/src/catalog.js`: 공개 도구와 JSON 입력 스키마를 소유한다. 변경 전 search_files는 query가 필수였고 extensions와 list_directory가 없었다.
- `lmstudio-unity-mcp/src/server.js`: 입력을 검증한 다음 파일 호출을 Files로 보내며, Editor Bridge와 독립적으로 실행한다.
- `shared-tool-core/files.js`: Files.search는 상대 경로 부분 문자열 검색에 선택적 본문 검색을 추가한다. 5,000개 파일 또는 10,000개 노드 제한 뒤 수집 결과를 페이지로 반환한다.
- `shared-tool-core/files.js`: page와 bounded가 결과 페이지 및 응답 바이트 제한을 담당한다. 현재 결과 해시만으로는 요청 경로와 필터가 다르지만 결과가 같은 검색을 구분하지 못한다.
- `lmstudio-unity-mcp/src/project.js`: Assets, Packages, ProjectSettings의 경로 허용 및 링크/경로 이탈 방지를 담당한다.
- `lmstudio-unity-mcp/test/runtime.test.js`: 임시 프로젝트와 실제 MCP stdio 경로를 검사하는 기반이 있다.
- 첨부 로그는 현재 실행 파일과 동일한 버전이라는 보장이 없다. 제안은 현재 저장소 소스를 기준으로 한다.

## 1. list_directory 추가

입력: path(필수), kind(선택: all/files/directories, 기본 all), limit, cursor, byteBudget.

- 지정한 폴더 바로 아래만 조회한다. 재귀/깊이 옵션은 추가하지 않는다.
- 기존 프로젝트 상대 경로 정책을 사용한다. 프로젝트 전체 가상 루트는 추가하지 않는다. 모델은 Assets, Packages, ProjectSettings를 명시한다.
- 항목은 재사용 가능한 상대 path와 kind만 반환한다. 본문, 하위 파일 수, 역할 설명을 반환하지 않는다.
- 이름순의 결정적 정렬을 사용하고 페이지 기본 50개, 최대 200개와 기존 바이트 제한을 따른다.
- kind=directories는 구조 개요에서 파일과 .meta 나열을 줄이는 명시적 필터다. 파일 종류를 서버가 자동 선택하지 않는다.
- 허용되지 않은 링크를 따라가지 않는다. 잘못된 경로, 파일을 폴더로 지정한 경우, 권한 오류는 명확한 오류로 반환한다.
- 직계 항목 열거에도 유한한 상한을 둔다. 상한에 걸리면 완전한 목록처럼 반환하지 않고 범위 초과 오류를 반환한다. 구체 상한은 기존 노드 한도 10,000을 재사용한다.
- 구현은 전체 하위 트리를 세지 않는다. 필요한 작업은 현재 폴더의 직계 항목 열거와 검증뿐이다.

## 2. search_files의 extensions 추가

extensions는 선택적 배열이며 1~16개 확장자를 받는다. 각 값은 점으로 시작하는 마지막 확장자다. 와일드카드, 경로, 복합 확장자는 받지 않는다. 확장자는 소문자로 정규화하고 마지막 확장자와 정확히 비교한다. 기존 query의 대소문자 구분은 유지한다.

| 입력 | 의미 |
| --- | --- |
| query만 지정 | 기존 경로 검색, content=true이면 본문 검색도 추가 |
| extensions만 지정 | 해당 확장자의 파일 경로 검색 |
| query와 extensions 지정 | 확장자 필터 후 기존 문자열 검색 |
| 둘 다 없음 또는 extensions=[] | invalid_arguments |
| content=true이고 query 없음 | invalid_arguments |

- extensions 안의 조건은 OR이며, path와 query 조건에는 AND로 결합된다.
- 확장자 생략 시 기존처럼 파일 종류 제한이 없다. .meta를 전역적으로 제외하지 않는다.
- .cs는 Foo.cs에 대응하고 Foo.cs.meta에는 대응하지 않는다. .meta를 명시하면 메타 파일도 조회한다.
- 본문 읽기 전에 확장자 필터를 적용한다. content=false 또는 생략이면 본문을 읽지 않는다.
- content=true에서 기존 경로 결과와 본문 행 결과가 함께 나오는 계약을 유지한다. limit과 total은 결과 행 수이며 고유 파일 수가 아니다.
- 파일 종류별 검색어/경로/개수가 다르면 모델이 별도 호출한다. 서버에 배치 계획 기능을 추가하지 않는다.
- 기존 파일/노드/누적 결과/바이트 제한을 유지한다. 확장자가 안 맞는다고 탐색 자원 한도를 무제한 우회하지 않는다.

## 3. 응답과 커서 계약 정리

- 기존 items, total, scanned, incomplete, truncated, nextCursor, revision을 유지한다. 같은 사실을 다른 이름으로 중복 추가하지 않는다.
- total은 이번 제한된 탐색에서 수집한 결과 행 수다. incomplete=true이면 요청 범위 전체의 총수가 아니다.
- truncated와 nextCursor는 이미 수집한 결과의 다음 페이지를 뜻한다. 미탐색 파일로의 이어받기가 아니다.
- incomplete=false도 단일 시점 스냅샷이나 모든 파일 본문의 판독 성공을 보증하지 않는다. 기존 per_file_observations와 본문 판독 제한을 설명한다.
- 혼합 확장자 검색은 통합 limit을 사용한다. 첫 페이지가 한 종류로만 채워져도 다른 종류의 부재를 결론 내리지 않는다.
- 목록/검색의 revision 계산에 프로세스 세션, 프로젝트 식별자, 작업 종류, 경로, 정규화한 필터와 관찰 결과를 함께 반영한다. page 자체에 별도 세션 저장소를 만들지 않는다.
- limit과 byteBudget은 페이지 크기 선택이므로 검색 식별 조건에서 제외한다. 조건이 바뀌거나 관찰 결과가 바뀌면 기존 snapshot_changed로 거절한다.
- 서버 업데이트 시 진행 중인 구형 커서는 실패할 수 있으며 첫 페이지를 다시 조회하도록 문서화한다. 자동 재시도하지 않는다.
- 미탐색 구간 재개, 캐시, 지속 인덱스는 이번 단계에서 추가하지 않는다. 페이지 재조회 시 재탐색 비용은 남는 한계다.

## 4. 수정 위치와 순서

1. 입력/응답 계약과 동작 검증 사례를 먼저 확정한다.
2. `shared-tool-core/files.js`에 비재귀 조회와 확장자 필터를 추가하고 목록/검색의 커서 식별을 보강한다.
3. `lmstudio-unity-mcp/src/catalog.js`에 list_directory와 확장된 검색 스키마를 등록한다. query 또는 extensions 필수 및 content 조건을 스키마와 런타임 경계에서 일관되게 검증한다.
4. `lmstudio-unity-mcp/src/server.js`에 list_directory의 파일 처리 분기를 연결한다.
5. `lmstudio-unity-mcp/test/file-discovery.test.js`를 추가해 실제 createRuntime 경로로 검증한다. 기존 runtime.test.js의 stdio 사례도 보강한다.
6. `docs/Unity_Setup.md`의 파일 탐색 계약/예시를 갱신한다. 이미 존재하는 작업 중 변경을 보존하며 관련 부분만 수정한다.

기존 Files, projectPolicy.resolve, page, bounded, read_file와 테스트 fixture 구조를 재사용한다. 새 파일 접근 정책, 실행기, 자동 탐색 계층을 중복 구현하지 않는다.

## 5. 검증 계획

| 사례 | 통과 조건 |
| --- | --- |
| Editor 미연결 | 폴더 조회와 파일 검색 성공, Bridge 호출 0회 |
| 비재귀 폴더 조회 | 직계 항목만 반환, 하위 폴더 내부 열거 및 파일 본문 읽기 0회 |
| 폴더 목록 필터/페이지 | kind 필터, 결정적 순서, 중복/누락 없는 페이지, 빈 폴더, 파일 경로 입력 오류 |
| 혼합 확장자 | .cs/.json/.prefab이 OR로 포함되고 .cs.meta는 .cs에서 제외 |
| 확장자만 지정 | 이름 조건 없이 경로만 반환, 본문 읽기 0회 |
| 기존 호출 | query만 사용하는 경로/본문 검색의 기존 결과 의미 유지 |
| 잘못된 조합 | 빈 배열, 잘못된 확장자, 무조건 검색, 검색어 없는 content=true 거절 |
| 페이지 편중 | 첫 페이지가 .cs뿐이어도 후속 페이지에서 .json을 정상 조회 |
| 부분 탐색 | 작은 합성 fixture 또는 격리된 파일 시스템 대역으로 제한 초과를 재현하고 incomplete/total/cursor 의미 검사 |
| 커서 혼용 | 결과가 같아도 다른 경로/검색어/확장자/작업의 커서는 거절 |
| 독립 호출 | Promise.all로 서로 다른 경로/종류 검색을 요청해 결과나 커서 상태가 섞이지 않는지 확인. CPU 병렬 실행 보장은 아님 |
| 자원/경로 제한 | 기존 응답 바이트, 링크 차단, 허용 루트 경계를 유지 |
| 실제 stdio | 도구 목록 노출과 새 입력 스키마, 호출 결과를 실제 MCP 클라이언트로 확인 |

실행 게이트: `node --test lmstudio-unity-mcp/test/*.test.js`.

패키지 검사: `python -m pytest tests/test_unity_package.py`로 변경된 소스가 기존 패키징 규칙에 포함되는지 확인한다. 새 실행 의존성이나 Editor 변경은 계획하지 않는다.

검증은 제한된 합성 프로젝트로 수행한다. 실제 프로젝트 전체 순회와 전체 소스 읽기를 완료 조건으로 삼지 않는다.

## 완료 조건과 남는 한계

- 모델은 폴더 두 단계와 필요한 소수 파일만으로 개요를 작성할 수 있다. 서버는 다음 대상을 선정하지 않는다.
- C#과 다른 파일 종류를 함께 또는 별도 조건으로 조회할 수 있다.
- 확장자만 찾을 때 본문이 응답이나 내부 읽기에 포함되지 않는다.
- 탐색 완료, 결과 페이지 완료, 고유 파일 수를 혼동하지 않는 계약과 예시가 마련된다.
- 위 테스트 및 패키지 검사가 통과하면 이번 변경을 종료한다.
- 모델의 실제 호출 선택과 종료 판단은 도구 계약만으로 보장되지 않는다. 실행 지침에는 상위 폴더부터 좁히고, 확인 범위를 명시하며, 개요 요청에서 전체 수집을 피하도록 짧게 안내한다.
- 구현 중 실패하면 배포 전에 중단하고 기존 변경을 보존한 채 이번 diff만 수정한다. 배포 후 되돌릴 필요가 있으면 catalog/server/core를 같은 버전 묶음으로 복원한다. 저장 데이터 마이그레이션은 없다.

## 구현 검증 기록

- `node --test lmstudio-unity-mcp/test/*.test.js`: 17개 중 15개 통과, 2개 생략. 생략된 사례는 별도 Roslyn 의미 분석 환경을 요구하며 이번 파일 탐색 변경과 관계가 없다.
- `python -m pytest tests/test_unity_package.py -q`: 1개 통과.
- 실제 MCP stdio 클라이언트에서 새 목록 도구 공개와 확장자 단독 검색을 확인했다. 혼합 확장자 검색은 createRuntime 테스트로 확인했다. 모델이 이 도구를 선택하고 적절히 멈추는지는 별도의 모델 실행 관찰이 필요하다.
- Windows에서 심볼릭 링크 생성 권한이 없는 경우 기존 테스트의 해당 확인만 생략하고, 나머지 하드 링크 및 경로 정책 검사는 계속 실행한다.
