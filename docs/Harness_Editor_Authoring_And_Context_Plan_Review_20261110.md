# 「에디터 구조 확인 하네스와 비율 기반 컨텍스트 관리」 계획 검토 (2026-11-10)

- **대상:** `docs/Harness_Editor_Authoring_And_Context_Plan_20261110.md`와 근거 JSON(codex 작업 폴더, 미커밋).
- **기준:** `Develop` `3116c07`. 이 검토는 소스 대조만 했고 코드는 바꾸지 않았다.
- **결론:** 방향과 원칙은 타당하다. 다만 그대로 구현하면 퍼센트 설정이 일부 경로에만 적용되고, provider 사전 검사는 계획대로 만들 수 없다. 아래 1–5번을 계획에 반영한 뒤 구현해야 한다.

## 2. 구현 전에 계획에 반영할 것

### 2.1 출력·안전 여유를 C의 비율로 만들 경로가 계획에 없다 (P1)
- 계획 9.3은 `O`와 `S`를 C에서 계산한다고 한다. 그런데 지금 `maxOutputReserve`와 `safetyMarginTokens`는 실행 시작 때 읽는 고정 설정값이고, C를 측정하기 전이나 측정과 무관하게 직접 쓰인다.
- `maxOutputReserve`를 직접 읽는 곳:
  - `context-manager.ts:120` (측정 자체의 출력 예약)
  - `delivery-controller.ts:117,121` (최종·이어쓰기 상한)
  - `prediction-loop.ts:411,1036,1499`
  - `round-input.ts:129,186,191,195`
  - `reasoning-recovery.ts:9` (상한의 2배)
  - `execution-config.ts:87` (이어쓰기 상한 기본값)
- 이대로 `BudgetBroker`만 고치면 압축 기준만 퍼센트가 되고 출력 상한은 절대값으로 남는다. 설정은 10%인데 실제 cap은 8192인 상태가 된다.
- **필요한 결정:** C를 처음 관찰한 시점에 "해석된 예산"을 한 번 만들고(C가 바뀌면 다시 계산), 위 지점이 모두 그 값을 읽게 한다. 이 객체의 소유자, 생성 시점, C를 못 읽었을 때의 값을 계획에 적어야 한다.

### 2.2 남은 공간 절대 기준은 새 방식에서도 살아 있다 (P1)
- 계획은 `softRemainingTokens`/`hardRemainingTokens`를 "숨은 절대 기준으로 동시에 적용하지 않는다"고만 적었다. 실제로는 hybrid와 deterministic에서도 이 값이 쓰인다.
  - `shouldCompactContext`가 `core.shouldCompact`를 OR로 묶는다: `context-manager.ts:191`, `direct-compaction-core.js:724`
  - `selectSoftCompaction`의 목표: `context-manager.ts:202-204`
  - hard 판정: `context-manager.ts:897`
- 계획에 이 세 지점을 명시하고, percentage 모드에서 각각 무엇으로 대체하는지 정해야 한다. 안 그러면 남은 공간이 6000 아래로 내려갈 때 시작률보다 먼저 압축이 걸린다.

### 2.3 기존 사용자와 새 설치를 구분할 방법이 없다 (P1)
- 설정에 버전 필드가 없다(`direct-config.ts`, `execution-config.ts`에 없음). 저장하지 않은 필드는 스키마 기본값이 반환된다.
- 따라서 새 필드 `contextBudgetMode`의 스키마 기본값이 곧 모든 기존 사용자의 동작이 된다. "새 설치는 percentage, 기존은 legacy 유지"는 `config.get`만으로는 구현할 수 없다.
- **필요한 결정:** 둘 중 하나를 고른다.
  - 기본값을 `legacy_auto`로 두고 사용자가 직접 전환한다. 동작 변화가 없다.
  - 기본값을 `percentage`로 두고 모든 사용자의 동작이 바뀐다는 것을 받아들인다. 이 경우 2.6의 동등성 수치를 릴리스 조건으로 둔다.

### 2.4 provider 사전 검사는 계획대로 만들 수 없다 (P1)
- 계획 5.5는 provider가 "규칙 버전, 대상 관찰, 변경 결정의 연결"을 확인한다고 한다. 같은 절에서 모델이 적은 ID는 믿지 않는다고도 한다.
- 구조 결정(`ArchitectureState`), 검토 기록, 근거 archive는 LM Studio 플러그인 프로세스에 있다. MCP provider는 별도 프로세스라 이 상태를 볼 수 없다. provider가 검증할 수 있는 것은 자기가 발급한 것뿐이다(Unity의 ObjectRef·receipt, Unreal의 파일 snapshot receipt).
- **필요한 결정:** 검사를 둘로 나눠 적는다.
  - provider: 대상 관찰 receipt와 자신이 제공한 규칙 hash만 확인한다. 모든 호스트에 적용된다.
  - 플러그인의 도구 경계: 변경 결정과의 연결을 확인한다. LM Studio에서만 적용된다.
  - 호스트별 보장 수준 표에 이 차이를 적는다.

### 2.5 설정 화면에는 실시간 토큰을 표시할 수 없다 (P1, SDK 확인 필요)
- 계획 9.2는 "%와 예상/실제 토큰을 함께 표시", 9.4는 "변환 미리보기"를 요구한다.
- 현재 설정 스키마는 고정 문자열(`displayName`, `subtitle`)만 쓴다. 로드된 C에 따라 바뀌는 값을 설정 화면에 그리는 경로는 이 저장소에 없다.
- **필요한 결정:** 요청 비율, 계산된 토큰, 실제 적용 비율, 조정 사유는 채팅의 디버그 정보나 상태 줄에 표시한다고 계획에 적는다. 설정 화면 표시는 SDK가 지원하는지 확인한 뒤에만 약속한다.

### 2.6 제안 기본값이 현재 동작과 거의 같다는 근거를 넣는다 (P2)
- 사용자의 실측 구성(C=84,224, 출력 8192, 안전 2048)에서 현재 적용값은 high 63,626(C의 75.5%), low 47,719(56.7%)다.
- 제안값(목표 55%, 시작 75%, 출력 10%, 안전 2%)으로 계산하면 high 63,168, low 46,323이다. 차이는 각각 −458, −1,396 토큰이다.
- 이 수치를 마이그레이션 예시와 회귀 fixture로 넣으면 "기본값 전환이 이 구성에서는 사실상 중립"임을 테스트로 고정할 수 있다.

### 2.7 출력 10%는 작은 컨텍스트에서 추론 모델의 보고를 자른다 (P2)
- C=32,768이면 출력이 3,276 토큰이 된다(현재 8,192). 기록된 실행에서 최종 보고 한 번에 추론만 7,586 토큰을 쓴 적이 있다.
- 출력 비율에 절대 하한을 둘지, 기존 `maxOutputReserve`를 하한으로 유지할지 정해야 한다. 32K에서 추론 모델로 최종 보고가 잘리지 않는지를 검증 표에 넣는다.

### 2.8 지금도 목표가 지켜지지 않는 원인을 단계 2의 완료 조건에 넣는다 (P2)
- 압축 직후 선택적 지침이 다시 들어와 최종 입력이 low를 넘는다. 실측에서 low 47.7K에 대해 48–53.6K였다.
- 목표 달성 판정이 설정 원시값과 비교한다: `prediction-loop.ts:611`(`targetMet`), `round-input.ts:609`. 텔레메트리도 원시값을 기록한다: `evidence-telemetry.ts:27-30`.
- 퍼센트로 바꿔도 이 경로가 그대로면 "설정한 목표율과 실제가 다르다"는 문제가 남는다. 완료 조건에 "압축 후 최종 입력이 목표 이하이거나 초과 사유가 기록된다"와 "판정·텔레메트리가 실제 적용값을 쓴다"를 넣는다.

### 2.9 C=8192 사례의 기대 결과를 분명히 한다 (P2)
- 리뷰용 도구 스키마만 5,689 토큰으로 측정된 적이 있다. C=8192에서 도구를 쓰면 필수 입력이 H를 넘는다.
- 이 사례의 합격 기준은 압축 동작이 아니라 "호출을 하지 않고 사유를 보고한다"여야 한다.

### 2.10 기각한 가설이 사라지는 지점은 압축이 아니라 턴 경계다 (P2)
- 검토 기록(`ReviewRegister`)은 실행마다 새로 만들고 저장하지 않는다(`prediction-loop.ts:156`, `toJSON`/`load` 없음). history 밖에 있어서 압축으로는 사라지지 않는다.
- 사라지는 경우는 두 가지다. 예산 때문에 fact가 생략될 때(우선순위 1), 그리고 사용자의 다음 메시지로 새 실행이 시작될 때다. "확인해서 수정해" 같은 후속 턴이 여기에 해당한다.
- 계획 8절에 턴을 넘는 보존 방식을 정해야 한다. 예: 읽기 장부처럼 `WorkingContext`에 저장하고 복원 시 historical로 표시한다.

### 2.11 규칙 문서의 크기 예산이 없다 (P2)
- `Human-Bartender/AGENTS.md`는 12,257바이트다. 항상 주입하면 필수 입력이 그만큼 늘고, 기록된 실행에서 필수 입력은 이미 10K에서 30K까지 커졌다.
- 계획 5.1에 전달 방식(요청 시 조회, 또는 적용 구간 발췌와 hash만 주입), 상한, 상한을 넘을 때의 동작을 적어야 한다.

### 2.12 구조 결정 기능은 기본 설정에서 꺼져 있다 (P2)
- `architectureEnabled`는 `designGuidanceMode === "auto"`를 요구하는데 기본값은 `off`다(`config-defaults.ts`의 `GUIDANCE_DEFAULTS`).
- Unity로 확장해도 기본 설정 사용자는 효과를 보지 못한다. 활성 조건을 계획에 적거나 지침 주입 설정과 분리해야 한다.

### 2.13 `prediction-loop.ts` 여유는 104바이트다 (P2)
- 현재 111,896바이트로 상한은 112,000바이트다. 2.1만 해도 이 파일의 세 지점을 바꿔야 한다.
- "연결만 둔다"는 원칙에 더해, 먼저 기존 코드를 담당 모듈로 옮겨 공간을 만든다는 순서를 적어야 한다.

### 2.14 단계 0에 기준 실측을 넣는다 (P2)
- `3116c07`에 필수 입력 구성과 투영 절감량 측정이 들어갔지만 실제 실행으로 본 적이 없다. 이전 수정의 실측 재실행도 아직 하지 않았다.
- 예산 방식을 바꾸기 전에 같은 프롬프트로 기준을 재야 한다. 그래야 이후 변화가 어느 변경 때문인지 가릴 수 있다.

## 3. 그대로 두어도 되는 부분
- 어휘(`Instantiate`, `NewObject`, 숫자 리터럴)를 신호로만 쓰고 금지로 단정하지 않는 원칙.
- 새 writer·브리지·archive·예산 계산기를 만들지 않는 원칙과 `doNotDuplicate` 목록.
- 관찰, 저장, 재로드, 실행을 따로 보고하는 상태 구분.
- off → observe → enforce 단계적 적용.
- 합성 replay와 실제 모델·에디터 결과를 분리하는 검증 방식.
