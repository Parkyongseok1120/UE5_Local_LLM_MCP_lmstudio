# 하네스 연속성 및 자원 관리 수정 계획

기준일은 2026-10-09이며, 대상은 현재 작업 트리다. Git HEAD는 78abd7fee5a1172b7bdb4d5e99c0dc3f51afbef8이지만 미커밋 변경을 포함하므로 커밋만으로 구현 기준을 재현할 수 없다. 상태는 **W1–W5 구현 및 자동 회귀 검증 완료, W6 실모델 성능 승인 미충족**이다. 승인된 원래 계획은 아래에 보존하고 마지막 절에 실행 결과를 기록한다.

목표는 긴 조사에서 읽은 범위와 분석 상태를 잃지 않고, 반복을 식별하여 설정된 경고·중단 정책을 적용하며, 실패한 실행의 자원을 정리하는 것이다. SSOT는 사실별 정본과 갱신 경로를 하나로 정한다는 뜻이다. 모든 상태를 하나의 거대한 관리자에 합치지 않는다. SOLID는 기존 책임을 더 명확하게 만드는 기준으로 적용한다.

기존 [전체 검토 계획](Harness_Full_Code_Review_Plan_20261007.md)과 [책임 및 수명 계획](Harness_Responsibility_Lifecycle_Plan_20261007.md)의 구현 완료 기록은 유지한다. 이번 계획은 아래 잔여 문제를 다루며, 이전의 원문 노출·핸들·취소 문제가 모두 미수정이라고 전제하지 않는다. 특히 “요약 실패 뒤 실행 전체 비활성화” 정책은 이번에 제한적인 재시도 정책으로 변경할 대상이다.

실행 기록의 스냅샷에서는 약 25분에 91개 조사 라운드가 진행됐고, 같은 Character.h 해시·바이트 범위를 여러 차례 다시 읽었다. Character.cpp 원문은 처음에 SDK 입력에 포함됐으며 12번째 라운드에 발췌로 바뀌었다. 요약은 21번째 라운드에 약 30초 타임아웃됐다. SDK 입력 포함은 모델의 이해 또는 검토 완료 증명이 아니다.

이 수치는 개선 전 기준이지 모든 라운드가 무의미했다는 판정이 아니다. 아카이브는 남아 있었고, 관찰한 완료 배치에서 영구 예약 누수는 확인되지 않았다. 설치·로드된 빌드는 작업 코드와 일치했다. [기준 및 근거 기록](evidence/harness-continuity-plan-20261009-baseline.json)을 따른다.

파일마다 인터페이스나 클래스를 추가하지 않는다. 새 범위 모듈은 TS 실행기와 CommonJS core가 공유해야 하는 실제 의존성 때문에만 도입한다. 같은 이유가 없는 facade, 전역 상태 저장소, event bus, 별도 메모 DB, 두 번째 계획 모델은 추가하지 않는다. Unreal C++ 변경이 필요해져도 프로젝트 지침에 따라 불필요한 namespace를 추가하지 않는다.

## 4 단계별 구현

### W0 기준 고정과 실패 사례 등록

현재 파일 해시·설정·빌드 식별자와 기존 테스트 결과를 기록한다. 공개 fixture에는 비공개 프로젝트 소스·개인 경로·receipt·capability를 넣지 않는다. 별도 감사 재현을 기존 테스트에 옮겨 기대 동작을 명시하되, 제품 수정과 함께 최종적으로 통과하도록 한다.

필수 사례는 바이트 읽기 압축 왕복, A/B 및 A/B/C 순환, 합법적인 페이지 증가, 발췌 뒤 재획득, 요약 타임아웃 뒤 새 근거, 두 읽기의 예약 경쟁, 초기화 실패한 자식 프로세스다. 기존 정책을 고정한 테스트는 삭제 대신 변경된 정책과 변경 이유를 함께 갱신한다.

완료 조건은 실행 전 기준을 재현할 수 있고, 어느 테스트가 결함 재현이고 어느 테스트가 정책 변경인지 구분되는 것이다. 새 제품 테스트는 기존 CI 등록 경로에 포함한다.

### W1 범위 계약과 결정적 연속성 수정

대상은 evidence-manager.ts, input-availability.js의 기존 범위 연산, compaction-tool-memory.js, continuity-file-observations.js, continuity-memory.js와 관련 contract다.

기존 닫힌 구간 연산을 공통 순수 모듈로 옮긴다. provider의 UTF-8 byte 반열린 구간은 경계에서 한 번만 변환하고, line은 기존 1-based 의미를 유지한다. 빈 구간은 읽은 한 글자로 바꾸지 않는다. UTF-16 archive offset, UTF-8 source byte, line, page, observation을 서로 변환·합산하지 않는다.

파일별 체크포인트에 단위·관측 범위·확인된 전체 길이·버전·완전성 근거를 가진 선택적 sourceCoverage 표현을 추가한다. 기존 줄 범위 필드는 같은 정본에서 파생하여 호환을 유지한다. byte offset과 다음 위치는 provider의 실제 반환에서만 가져온다. 단순 hasMore=false 또는 EOF 페이지 하나만으로 전체 파일을 읽었다고 만들지 않는다.

범위 병합 키에는 provider/project/source/query/version/representation/unit을 반영한다. 같은 경로라도 버전이 바뀌면 신규 관측으로 처리하고 이전 분석 주장의 유효성을 재평가한다. 버전이 불명확한 결과를 다른 결과와 합쳐 전체 읽기 완료로 만들지 않는다.

빈 필드인 이전 체크포인트는 unknown으로 읽는다. 새 필드는 자체 형식 버전을 갖고, 구형 reader가 모르는 필드를 무시해도 기존 권한·쓰기 검증은 유지되어야 한다. 헤드리스 core가 GUI의 SDK 코드나 TS dist를 필요로 하지 않게 한다.

완료 조건은 partial→partial, 전체 합집합→complete, 버전 변경→별도 관측, 오류/빈 페이지→진척 없음이 byte와 line 양쪽에서 성립하는 것이다. 원문 아카이브 범위와 실제 소스 범위는 독립적으로 검증한다.

### W2 일반 조사와 복구의 진척 관측 통합

EvidenceManager에서 확정된 반환 쌍을 한 번만 수용하고 같은 결과를 일반 조사·복구·telemetry에 전달한다. 복구 진입 시 실행 전체 coverage를 초기화하지 않고 복구 구간의 기준점만 둔다. callback 종료·취소·중복 결과에 대한 기존 RoundTransaction/pairing 규칙을 유지한다.

신규 소스 범위, 신규 archive 범위, 현재 입력에서 빠졌다가 다시 얻은 범위, 이미 현재 입력에 있는 중복, 실패를 분리한다. 현재 구현의 currentInputAvailabilityGain=null을 추정 숫자로 바꾸지 않는다. 최종 입력의 단위별 가용 범위와 비교한 경우에만 확인된 이득을 기록한다.

순환 감지는 제한된 최근 관측 창에서 동일 버전·동일 쿼리·중첩 범위 반복을 검사한다. 초기 평가값은 최근 8개 완료 도구 라운드 안에서 같은 2~4단계 패턴이 두 번 이상 반복되고 신규 소스 범위가 없는 경우다. 합법적인 페이지 증가·새 버전·새 검색 조건은 반복으로 취급하지 않는다. 단순 경과 라운드 수로 새로운 의미적 결론의 부재를 단정하지 않는다.

재획득은 현재 입력을 복구한 진척으로 인정하되, 같은 집합의 축약→재획득이 반복되면 별도 사유를 남긴다. 메모의 문구 변화나 새 call ID만으로 신규 근거 카운터를 초기화하지 않는다. 보관 상한 때문에 잊은 항목은 unknown으로 취급하며 반복 확정에 사용하지 않는다.

기존 toolStagnationAction의 off/warn/pause를 존중한다. warn은 같은 사건에 경고를 반복 주입하지 않고 알려진 범위·부족한 범위·재획득 이유를 작은 피드백으로 전달한다. pause는 ExecutionState와 기존 종료 경로를 통해 부분 상태를 전달한다. 제한된 audit 모드에서만 기존 최종 보고 기회를 사용하며, 보고 자체를 taskCompleted=true로 승격하지 않는다. 기본 warn을 몰래 강제 중단으로 바꾸지 않는다.

완료 조건은 A/B/A/B와 A/B/C 순환을 잡고, 페이지가 실제로 전진하는 시나리오와 필수 fresh read는 막지 않는 것이다. 일반 조사와 복구가 동일 반환 결과를 두 번 계산해서 진척을 부풀려서는 안 된다.

### W3 요약 실패와 압축 경계의 계약 수정

semantic-handoff가 같은 의미 사건의 시도 여부·실패 이유·실행 예산을 관리한다. 기존 lastSummaryInput의 중복 방지는 유지하면서 전체 실행 무기한 cooldown을 제거한다. 타임아웃, 출력 한도, 무효 note, 사용자 취소를 구분한다.

같은 사건은 재시도하지 않는다. 새 버전·새 범위·실질적으로 변경된 체크포인트가 있고 cooldown과 잔여 예산을 모두 만족할 때만 후속 시도를 허용한다. 초기 평가값은 한 실행에서 요약 모델 호출 최대 2회, 합산 대기 최대 60초, 실패 후 최소 3개 완료 라운드다. 값은 config-defaults의 정책 정본에 두고 UI 설정은 필요성이 입증된 것만 노출한다. 호출·토큰·시간 예산을 함께 기록하고 finalization·취소 뒤에는 시도하지 않는다.

요약이 필요한 사건은 단순 메시지 수가 아니라 의미 있는 근거를 입력에서 제거하는 압축/발췌 경계로 정의한다. 기존 체크포인트 생성기와 summaryEvidence를 재사용해 축약 전의 제한된 후보를 구성한다. 각 발췌마다 모델 호출을 추가하지 않고 사건 중복·예산 정책을 통과한 경우에만 호출한다. 후보 생성과 최종 입력 채택은 기존 ContextManager의 fit 검사를 따른다.

유효한 기존 note는 새 요약이 실패해도 보존한다. note가 없으면 “분석 메모 없음”과 이미 관측한 범위·열린 작업을 결정적 사실로 전달한다. 요약 성공을 원문 축약의 무조건적 선행 조건으로 삼아 context 초과를 유발하지 않는다. 요약은 검증된 ref에 연결된 모델 주장으로만 취급한다.

시도 사건은 기존 window 저장 경로에 제한된 형태로 보존하여 동일 사건을 복원 직후 다시 호출하지 않게 한다. 저장된 wall-clock deadline을 새 실행에 그대로 적용하지 않는다. 신규 실행의 예산과 동일 사건의 중복 방지를 분리한다. 핸들·receipt·raw reasoning은 영속 저장에 추가하지 않는다.

완료 조건은 실패 후 같은 사건 재호출 0회, 조건을 만족한 새 사건에 한정된 재기회, 실패 시 기존 note 유지, restore/취소/최종 보고에서 중복 호출 없음이다. 제안한 수치의 효과는 실제 비교 평가 후 확정한다.

### W4 읽기 예산과 모델 피드백 정리

BudgetBroker는 예약과 clamping의 정본으로 유지한다. provider schema는 field의 단위·최소·최대·기본 반환 계약을 제공하고, broker의 보수적인 token 비용 정책은 별도로 유지한다. 안전 여유와 UTF-8/JSON 비용 계수를 근거 없이 낮추지 않는다.

기존 tool trace에 원래 요청 한도·허용된 한도·단위·거부 사유를 명시하고, 실제 반환 후 envelope 크기와 본문 크기를 함께 기록한다. 모델에게는 필요한 경우에만 작은 실행 피드백을 전달한다. provider가 알 수 없는 최초 요청값을 provider 결과로 꾸며 넣지 않는다.

archive maxChars의 기존 전체 응답 상한 의미를 유지한다. body view의 실제 범위와 nextOffset은 원본 반환 그대로 제공한다. 공유 예산이 최소 유효 본문을 담지 못하면 메타데이터만 반복 반환하지 말고 구조화된 사유를 제공한다. 다음 모델 라운드 준비 단계에서 ContextManager가 읽기 공간을 확보하고 재측정한다. broker와 archive가 각자 다른 임의 “최소 본문” 값을 갖지 않게 공개 읽기 계약을 공유한다.

같은 배치의 held 예약 때문에 거부된 경우와 전체 남은 예산 부족을 구분한다. 완료된 동료 호출 결과는 채택한다. 이미 실행된 요청의 자동 재전송, 새로운 직렬 실행 스케줄러, 두 번째 예약 장부는 만들지 않는다. mutation 결과 미확인 상태에는 이 읽기 최적화를 적용하지 않는다.

완료 조건은 Unicode·JSON escaping·긴 경로·작은 예산에서도 envelope 상한 준수, 정확한 이어 읽기, 예약 1회 정산, 라운드 종료 후 held=0, 메타데이터만 읽는 반복의 명시적 감지다.

### W5 헤드리스 수명과 공개 근거 수정

McpProcess.start가 subprocess 생성 이후 초기화 예외를 포함해 정리 책임을 갖게 하고, main의 정리 목록 등록은 start 호출 전에 수행한다. close는 부분 초기화·중복 호출·이미 종료된 child에도 안전해야 한다. terminate 뒤 wait, 필요할 때 kill 뒤 wait까지 끝내고 열린 pipe를 정리한다. 초기화의 본래 오류를 정리 오류로 덮지 않는다.

첫 서버 실패, 두 번째 서버 실패, handshake 거부, EOF, timeout, 사용자 중단을 시험한다. 이 경로에서 종료하는 대상은 실행기가 생성한 child로 한정한다. 기존 사용자의 Editor나 LM Studio 프로세스는 종료하지 않는다. Windows에서 단독 headless client 지원을 확대하는 일은 별도 범위이며, 현재 지원 경로와 portable failure fixture를 구분한다.

기존 공개 증거 JSON의 개인 경로는 repository-relative 위치 또는 명시적인 비식별 실행 ID로 바꾼다. 로컬 원시 로그 위치는 배포하지 않는 manifest에 둔다. 경로를 숨기려고 public-path 검사에 예외를 추가하지 않는다.

완료 조건은 초기화 실패 뒤 살아 있는 owned child가 없고, 현재 작업 트리의 public path 검사가 통과하는 것이다.

### W6 회귀 검증과 도입

각 단계의 관련 테스트가 통과한 뒤 합쳐서 기존 전체 suite를 실행한다. npm test의 명시 목록과 전체 test 디렉터리의 차이는 기존 CI 경로에서 확인하고 필수 제품 테스트 누락을 막는다. 별도 수작업 목록을 더 만들지 않는다.

변경한 config·contract·생성 identity·패키지 파일·설치 검사까지 연결한다. generated 파일은 생성기로만 갱신한다. 설치 소스와 실제 로드된 build ID를 다시 비교해야 라이브 평가 결과를 새 코드의 효과로 인정한다.

문서의 구현 결과는 실제 통과 항목과 남은 경계를 갱신하며, 이 계획의 제안값을 검증된 성능으로 바꾸어 쓰지 않는다.

## 5 의존 순서와 변경 단위

주 경로는 W0 → W1 → W2 → W3 → W4 → W6이다. W5는 W0 이후 독립적으로 처리할 수 있다. 코드 이동과 동작 변경은 가능한 한 분리한다. 각 단계가 검증된 뒤 다음 단계로 진행하여 회귀 원인을 좁힐 수 있게 한다.

| 변경 단위 | 최소 검토 산출물 |
| --- | --- |
| 범위 정규화와 체크포인트 | 구형 자료 왕복, byte/line 동등 사례, version invalidation |
| 단일 진척 관측과 순환 정책 | 한 번 수용 보장, 일반/복구 동등성, 합법 재독 반례 |
| 요약 정책과 축약 경계 | 사건별 시도 표, 비용 한도, restore/취소 결과 |
| 읽기 예산 피드백 | requested/effective/body 구분, 경쟁·정산·페이지 끝 사례 |
| 헤드리스와 배포 문서 | 프로세스 실제 종료, 본래 오류 보존, 공개 경로 검사 |
| 통합과 설치 검증 | 전체 테스트 결과, 생성물 일치, live build ID, 전후 비교 |

기존 변경을 일괄 되돌리거나 사용자 작업을 재작성하지 않는다. 데이터 형식은 추가 필드와 보수적인 구형 reader로 먼저 도입한다. 동작 정책만 이전 구현으로 되돌릴 때도 이미 저장된 window와 archive를 삭제하지 않는다. 읽을 수 없는 새 필드는 unknown으로 낮추고 확인되지 않은 읽기·검토 완료를 추정하지 않는다.

## 6 필수 불변 조건

- 실제 원문 관측, 현재 SDK 입력 포함, 모델 분석 완료, 사용자 작업 완료는 서로 다른 사실이다.
- source version·query·단위가 다른 범위를 합치지 않는다. archive offset을 원본 byte offset으로 사용하지 않는다.
- 원문을 발췌로 바꾸어도 접근 가능한 근거와 결정적 진행 상태를 유지한다. 접근 실패는 unavailable로 남긴다.
- 같은 확정 반환 쌍을 두 번 수용하지 않는다. 취소된 요청의 미수신 효과는 unknown으로 남긴다.
- 모든 모델 호출은 최종 입력의 fit·출력 여유·실행 취소를 확인한다.
- 요약 실패가 기존 유효 note를 지우지 않는다. 요약 재시도는 사건·횟수·시간·토큰 한도를 가진다.
- 정상 pagination, 변경된 파일 재확인, mutation을 위한 fresh read를 반복 감지 때문에 무조건 막지 않는다.
- off/warn/pause와 bounded audit의 명시 설정을 유지한다. 강제 중단은 기존 실행 상태 소유자가 처리한다.
- 예약은 한 번만 정산하고 종료 후 후속 callback이 상태를 다시 변경하지 못한다.
- source SHA, 정제된 archive hash, read handle, write receipt의 의미와 권한을 섞지 않는다.
- provider 간 의미를 추측하지 않는다. 확인되지 않은 부분은 unknown이며 테스트 통과를 전체 감사 완료로 승격하지 않는다.
- 공개 문서·fixture에 개인 경로, 실제 비공개 소스, 인증값을 추가하지 않는다.

## 7 검증과 완료 기준

| 층 | 필수 검사 | 통과 조건 |
| --- | --- | --- |
| 순수 계약 | 구간 대수, Unicode, empty/partial/full, 다른 version/query/unit | 잘못된 병합·완료 승격 없음 |
| 상태 통합 | 실제 round-input/prediction-loop, 압축·복원·일반/복구 전환 | 결과 1회 수용, 원문과 가용성 분리 |
| 요약 실패 | timeout, invalid refs, output limit, aborted, restart | 제한된 시도와 기존 note 보존 |
| 예산 | 작은 응답, 병렬 경쟁, 중간 실패, 취소 | exact fit 유지, 정확한 거부 사유·정산 |
| 프로세스 | 무해한 실제 child의 init 실패/EOF/timeout | owned child 종료 확인, 오류 보존 |
| 호환 | 이전 window/checkpoint/config와 legacy/deterministic/hybrid | 보수적 읽기, 기존 off 유지, 권한 확대 없음 |

| 라이브 | 동일 모델·context·prompt·fixture·읽기 설정으로 전후 비교 | build 일치와 품질·비용 변화 확인 |

기준 자동 결과는 Compactor 643 통과, Unreal 277 통과/1 skip, Unity 52 통과/4 skip, Python 1,137 통과/1 실패/19 skip이다. 이는 앞선 감사 실행 결과이며 이번 계획 작성에서 전체 suite를 다시 실행한 결과가 아니다. 개발 기준 Node 20/Python 3.12에서 필수 검사를 확인하고, 이전 감사에 사용한 Node 24 결과와 혼동하지 않는다.

라이브 평가는 기존 eval-audit-pressure 및 input-availability 평가 도구를 확장한다. 짧은 합법 pagination, 파일 순환, 요약 실패 후 새 근거, context 압력으로 인한 재획득을 포함한다. 고정 fixture를 사용하고 baseline/new를 같은 설정에서 비교하며 cold/warm 상태를 기록한다. 비결정적 모델 평가는 사례별 최소 3회로 중앙값과 범위를 함께 본다.

측정값은 provider별 신규 범위, 현재 입력 복구량, 동일 version/range 재독, 요약 호출 수·실패·비용, prompt 처리 시간, 누적 입력 토큰, 거부 원인, 부분 보고/최종 보고 구분이다. 서로 다른 단위의 범위를 합쳐 “진척 점수”를 만들지 않는다.

하드 기준은 데이터 손실·허위 완료·무제한 재시도·프로세스 누수·예산 초과가 없는 것이다. 개선 목표는 순환 fixture의 불필요한 재독을 기준 대비 절반 이하로 줄이고, 신규 근거 수집 범위를 줄이지 않는 것이다. 모델 품질이나 비용 개선이 없으면 그 정책은 검증 완료로 보지 않고 조정한다. 임의 라운드 제한으로 검토를 일찍 끝낸 것을 개선으로 계산하지 않는다.

Live Editor 변경·Unreal 빌드·Unity domain reload와 외부 Roslyn은 실제 변경 영향에 맞춰 별도 검증한다. 이 계획의 자동 단위 시험만으로 해당 환경의 완료를 주장하지 않는다.

## 9 구현 결과와 검증 한계

2026-10-09 사용자 승인 뒤 기존 미커밋 작업을 보존하며 구현했다. 새 Unreal C++ 네임스페이스는 추가하지 않았다. 범위 연산·archive 응답 계약·요약 시도 정책만 작은 공통 모듈로 추출했고, 기존 EvidenceManager / ContextManager / BudgetBroker / WorkingContext의 책임을 유지했다.

- W1: utf8_byte/line 범위와 이어 읽기를 체크포인트에 보존한다. 버전·provider·query가 다른 범위를 합쳐 완료로 승격하지 않는다. 옛 line 필드도 새 범위 계약에서 파생한다. 복원된 읽기 이력은 현재 SDK 원문으로 승격하지 않는다.
- W2: 일반 조사와 복구가 같은 라운드 관측을 소비한다. 짧은 읽기 순환과 새 페이지·새 버전·현재 입력 재획득을 구분한다. 버전 없는 디렉터리 결과는 내용 fingerprint까지 비교한다. off/warn/pause를 실제 예측 루프에서 검증했다.
- W3: 같은 근거의 새 호출 ID는 새로운 요약 사건이 아니다. 실패 후 3라운드 cooldown, 실행당 최대 2회/합산 60초 예산, 최대 32개 사건 기록을 공통 정책으로 둔다. 이전 note와 기존 window 저장 경로를 유지한다. 이 수치는 최적 성능을 입증한 값이 아니다.
- W4: 원래 요청 한도와 계약/공유 예산을 적용한 실행 한도를 구분한다. 전체 응답 크기와 본문 크기를 따로 기록한다. archive는 다음 페이지를 읽을 수 있을 만큼의 본문을 제공하지 못하면 명시적인 예산 오류를 반환한다.
- W5: MCP 초기화 이전부터 자식 프로세스의 정리 책임을 등록하고, 실패·EOF·timeout·중단 시 reap과 pipe 정리를 검증했다. 공개 증거의 개인 경로를 제거했다.
- W6: Node 테스트 목록을 파일 발견 방식으로 통일하고, 중복 실행되던 Astra test import를 제거했다. 배포 필수 목록에 새 공통 모듈을 연결했다. 실제 모델 평가의 가상 경로 자동 감지 오류를 수정하고 회귀 검사를 추가했다.

독립 검토에서 확인한 line scope 혼합, 버전 없는 관측의 잘못된 순환 판정, 읽기 제한의 원래 요청값 손실 세 항목을 수정했다. 체크포인트·예산·프로세스 상태의 결정적 검증과 실제 모델의 품질 평가는 구분한다.

현재 Node 20.20.2에서 Compactor 647 통과, Unreal MCP 277 통과/1 skip, Unity MCP 52 통과/4 skip, 루트 Node 6 통과를 확인했다. TypeScript, guidance/identity, 수정 Python의 lint, encoding, 개발 패키지 생성도 통과했다. Python 최종 전체 검증은 1,144 통과/0 실패/19 skip으로 확정했다. 합계 2,126 통과/0 실패/24 skip이며, skip은 Windows에서 실행할 수 없는 POSIX/macOS 계약과 설정하지 않은 실제 Editor/Roslyn 환경이다. 패키지 재현성 검사도 소스를 고정한 재실행에서 통과했다. 기존 package builder 파일의 변경하지 않은 lint 3개는 이 수정의 신규 오류로 취급하지 않았다.

실제 모델 비교는 이미 로드된 swift-1.5-qwen3.8-27b에 고정 fixture·시드·설정을 적용한다. provider가 제외된 초기 평가 결과는 무효로 보관한다. 전체 정책의 성능 승인 조건, 특히 재독 절반 감소 및 답변 품질 유지, 설치된 LM Studio 채팅의 실행 확인은 아직 충족됐다고 주장하지 않는다. 제품 소스 수정과 로컬 시험은 실제 설치본 활성화의 증거가 아니다.

구현 근거는 [범위 및 순환](evidence/harness-continuity-implementation-20261009-coverage.json), [요약 및 예산](evidence/harness-continuity-implementation-20261009-policy.json), [수명 및 통합 검증](evidence/harness-continuity-implementation-20261009-lifecycle.json)에 기록한다. 구현 직전 사본과 원시 실행 로그는 공개 배포에서 제외된 로컬 감사 폴더에 보존한다.


최종 검증 기록은 [검사 수치 및 실행 비교](evidence/harness-continuity-verification-20261009.json)에 저장했다. 실제 모델은 각 조건 3회, 총 6회를 실행했지만 전부 100초 제한으로 종료되어 완성된 답변이 없었다. 후보 수정본의 과거 원문 재획득 중앙값은 1,110줄, 기준본은 1,361줄이었으나, 이 재획득은 현재 입력에 없는 근거를 되찾는 행위도 포함하므로 불필요한 재독 감소율로 해석하지 않는다. 답변 품질 유지나 재독 절반 감소 조건은 미충족이다.

실모델 비교에 로드한 후보는 마지막 독립 검토의 세 수정 이전 빌드다. 최종 빌드는 `ef-build-v2-4f16d2122b43602f6f1bbe76cd766a4f82ec6f725130d1c95a12cc3e6c072d3b`로 647개 컴팩터 테스트를 통과했다. 설치본은 이전 `ef-build-v2-1066996bbe3673c4b166e72845ce9738fe43376c65fb82a087aca99e74ddbfe2`로 유지했다. 전체 실모델 성능 검증이나 실제 LM Studio 채팅 적용 완료로 표시하지 않는다.
