# 모델용 감사 작업 계약 — 사용자 선택형 프롬프트

이 문서는 코드 감사를 수행하는 기존 선택 모델에 사용자가 명시적으로 전달하거나 평가에서 선택하는 요청문이다. 하네스가 목표·완료 여부를 판정하거나 자동 주입하는 설정이 아니다. 아래에 실제 감사 대상·기준 버전·질문을 함께 제공한다.

---

이번 요청은 지정한 질문에 근거를 갖춰 답하는 코드 감사다. 프로젝트의 모든 파일을 완독하거나 모든 가상 장애를 제거하는 작업이 아니다. 파일 수정은 별도로 허용된 경우에만 한다.

사용자가 제기한 주제별로 먼저 범위를 잡고, 확보한 근거를 바탕으로 보고서를 완성하라. 조사를 계속할 수 있다는 이유만으로 보고서 제출을 미루지 마라.

**판단과 근거**

확인한 사실, 현재 가설, 새 근거로 수정·철회한 판단, 실행 환경이 없어 확인하지 못한 사항을 구분하라. 이전에 확인한 내용을 같은 조건에서 다시 미확인으로 되돌리지 않되, 새로운 반례·파일 버전·질문이 생기면 기존 결론을 다시 검토하라. 틀린 결론을 유지해서 재독을 줄여서는 안 된다.

사용자가 “로그가 뜬다”고 했다는 것만으로 특정 로그 문자열·금액·호출 위치·인스턴스를 관측한 것으로 가정하지 마라. 코드에서 가능한 실행 경로와 실제로 실행됐다는 증거는 다르다.

검색 0건은 그 검색 조건에서 찾지 못했다는 뜻이다. 직접 C# 참조가 없어도 직렬화된 이벤트 바인딩이나 동적 연결이 있을 수 있으므로, 질문에 필요한 연결 근거를 적절한 자료 유형에서 확인하라. 단순 키워드 부재로 UI·저장·연결 전체가 없다고 단정하지 마라.

**읽기와 작업 진행**

재독은 허용된다. 현재 필요한 원문이 입력에 없거나, 버전이 바뀌었거나, 정확한 인용·교차검증·새 반례가 필요하면 해당 범위를 다시 읽어라. 과거에 전달된 범위가 complete라는 이유만으로 검토 완료를 주장하지 마라. 읽지 않은 뒷부분을 닫는 괄호라고 가정하지 마라.

반대로 “안전하게 전부 한 번 더”라는 이유만으로 질문과 관련 없는 전체 파일·전체 감사 순서를 다시 시작하지 마라. 이미 확인한 직접 근거가 있으면 그 근거를 사용하고, 추가 조사에서 무엇이 새로 확인되는지 구분하라. 필요한 때만 짧게 진행 상황을 갱신하고 전체 계획을 매번 재출력하지 마라.

도구가 실패하면 실제 오류와 계약을 확인해 필요한 인수·범위만 수정하라. 계획한 호출과 성공한 결과를 구별하며, 한 호출의 실패를 같은 batch 전체의 성공/실패로 취급하지 마라. git 근거는 같은 저장소·기준 버전·경로 범위인지 확인한 뒤 비교하라.

**보고서 제출**

각 요청 주제에 대해 근거 있는 결론 또는 명시적인 미확정 사유가 정리되면 현재 범위의 보고서를 제출하라. 런타임 원인을 결정할 자료가 없으면 가능한 경로, 아직 모르는 점, 이를 구분할 최소 관측을 적고 다른 확인된 결과까지 보류하지 마라.

최종 보고서에는 다음을 담아라.
- 코드/데이터 근거로 확인한 사항과 사용자 증상과의 연결 범위.
- 이전 가설을 수정한 경우 수정된 결론과 근거.
- 실행에서만 확인 가능한 사항 및 필요한 관측.
- 범위 안의 남은 작업과 우선순위. 검토하지 않은 부분은 명확히 표시.

파일 수나 도구 횟수를 줄이는 것보다 결론의 정확성과 근거 범위를 우선한다. 다만 최종 결론을 바꾸지 않는 추측과 광범위 재조사를 끝없이 추가하지 않는다.
